
# 规模与正确性设计 · 十人 → 千万级（获客 OS）

> 北极星不变：获客莫比乌斯 + 商业正循环  
> 问题：租户多了以后抗不抗得住？不同场景请求如何尽量不出错？  
> 日期：2026-09-14

---

## 1. 规模分层（先认清每一层要什么）

| 量级 | 大概含义 | 系统压力 | 架构重点 |
|------|----------|----------|----------|
| **10 人/租户** | 内部/种子客户 | 低 | 功能正确、体验好、数据真 |
| **百** | 小规模付费 | 中 | 任务队列、基础监控、备份 |
| **万** | 增长期 | 高 | 水平扩展、租户隔离、缓存、限流 |
| **十万+** | 平台期 | 很高 | 分片、多区域、SLO、混沌演练 |
| **千万** | 超大规模 | 极高 | 事件驱动、最终一致、单元化、成本治理 |

**原则**：不要为 10 人租户上千万架构；但**接口与数据模型从第一天就要按可扩展设计**（现在细胞级总谱就是在做这个）。

## 2. 现仓怎么走到「扛得住」（演进路线）

### 2.1 当前形态（先认清）

- FastAPI 单体 + PG@5433 + Redis + Celery + n8n  
- 多租户：Host/JWT → `tenant_id`，应用层过滤（RLS 可选试点）  
- 编排：爱马仕 + `ai_tasks`  
- 水平扩展未做满；这是演进点不是缺陷  

### 2.2 量级演进（每步可验证）

```
10~100 租户
  单 PG + Redis + 2~4 worker
  全链路幂等 + 指标基线

1000~1万 租户
  PG 主从读写分离（已预留 DATABASE_READ_URL）
  Celery 按队列扩容（获客/内容/履约分开）
  Redis 缓存热点（租户配置、Playbook、技能包）
  连接池 + 查询索引审计（cell 级）
  API 网关限流：按租户配额

1万~10万
  按租户或租户桶分片（逻辑库/Schema）
  热点隔离：大租户独立 worker 池
  对象存储/静态走 CDN
  异步化：所有非同步必须业务的接口变「受理+轮询」
  搜索/列表：读模型或缓存物化（OpsCard 投影）

10万~1000万
  单元化：区域单元（例如按国家/大区）
  事件总线：获客事件进流处理，回写最终一致
  多活/同城双活 + 故障切换演练
  成本：按租户算 Token/IP/存储毛利
  SLO：99.9% API / 99% 任务成功（可配置）
```

## 3. 「不同场景请求」如何正确处理

### 3.1 请求类型与一致性要求

| 场景类型 | 例 | 正确性要求 | 手段 |
|----------|----|------------|------|
| **查询** | 看跟单卡、线索列表 | 读到最新可接受版本 | 缓存短 TTL + 失效；关键读可走主库 |
| **写业务** | 批准外联、改收款状态 | **强一致、幂等** | 事务 + 幂等键 + 版本号 |
| **编排任务** | from-intent 拓客图 | 状态可追溯、可恢复 | ai_tasks 状态机 + 断点续跑 |
| **外发** | 邮件/WA/发布 | **绝不双发、绝不假成功** | 幂等 + 外发台账 external_ref + 人审 |
| **计费** | Token/IP 槽位 | 对账可解释 | meter 账本 + 双记防护（历史已强调） |
| **LLM 出图/写信** | DSH 拆解、千人千面 | **结果合法才采用** | Schema + 安全阀 + 人工门禁 |

### 3.2 「完全正确」的工程定义（务实）

系统**不可能**数学意义 100% 永不出错，能做到的是：

| 目标 | 含义 |
|------|------|
| **状态正确** | 每个单子状态机合法，可回放 |
| **数据不丢** | 写入落库 + 备份 |
| **不双写副作用** | 外发/扣费幂等 |
| **不假成功** | 失败必须 failed/degraded 可见 |
| **租户不串数据** | tenant_id 强制 + 测试 |
| **可解释** | 为什么返回这个结果：trace + 输入摘要 + 规则/技能版本 |
| **可纠错** | 补偿、回滚 Canary、人工修正入口 |

**「完全正确返回」在产品上 = 合法输入 → 契约内输出；非法/缺失 → 明确错误或降级说明，而不是瞎编。**

## 4. 保证不出错的技术细胞（与总谱衔接）

| 细胞 | 作用 |
|------|------|
| **契约** | API/节点 JSON Schema（细胞 A/N） |
| **幂等键** | outreach/inquiry/payment/slot |
| **乐观锁** | 跟单卡/阶段 version |
| **租户隔离测试** | IDOR/跨租户读写单测必过 |
| **安全阀** | 爱马仕 validate_graph 白名单/防环 |
| **人审** | 外发/改价/经验晋升 |
| **审计日志** | 谁在何时改了什么 |
| **金丝雀** | Skill/模板 5→25→50→100% |
| **SLO 与错误预算** | 允许波动，但可测可报警 |
| **混沌/压测** | locust 已有雏形；按场景压 from-intent、发送队列 |
| **限流配额** | 每租户 QPS、日发送、Token 预算 |
| **熔断** | 外部 TradeAI/GoodJob/翻译失败 → 诚实 degraded |
| **回放** | plan_id + 节点输入输出可重放核对 |

## 5. 并发与「万级同时」场景

| 问题 | 解法 |
|------|------|
| 突发询盘/任务 | 队列削峰（Celery 队列分离：outreach / content / ops） |
| 大租户挤小租户 | 按租户公平调度 / 大租户独立池 |
| 热点配置 | Playbook/技能包 Redis + 版本 |
| 数据库锁 | 短事务；状态更新用条件 UPDATE |
| LLM 吞吐 | 网关限流 + 降级 L3 兜底图；付费档位限并发 |
| 发送风控 | 全局限速按 IP/域名/租户，防一封搞垮全平台 |

## 6. 不同规模下的「正确性验收」

| 阶段 | 必测 |
|------|------|
| 10 | 单租户 E2E：线索→信→询盘→跟单卡→PI |
| 百 | 多租户隔离 100 用例；幂等 1000 次重试 |
| 万 | 压测：1k RPS 读 / 百任务并发编排；无串租户 |
| 十万 | 故障注入：杀 worker、断 Redis、TradeAI 超时 → 诚实降级可恢复 |
| 千万 | 单元化演练；跨区一致；成本与 SLO 看板 |

## 7. 与「万能编排」的关系

```text
请求风暴
  → 网关限流/鉴权
  → DSH：意图归一（快路径规则优先，LLM 削峰）
  → 爱马仕：图校验 → 队列 → 执行器池水平扩
  → 契约输出；失败诚实
  → 指标/审计/经验（经验写入也要限流与批处理）
```

编排「串联 > N」在规模下依然成立：**字母一样，执行器可横向复制；调度权仍在爱马仕单点逻辑（可多副本无状态 + 图状态在 DB）。**

## 9. 一句话回答主理人

- **10～百**：先把**正确性细胞**做实（幂等、隔离、诚实失败、可追溯），单机栈通常够用。  
- **万**：队列扩容 + 读写分离 + 配额限流，架构已预留。  
- **十万～千万**：分片/单元化/事件化，按流量演进，不是今天写死千万架构。  
- **「不出错」**：靠契约、状态机、幂等、人审、金丝雀、审计与压测，**不是靠祈祷**；对用户表现为「合法结果或明确降级，永不假成功」。
