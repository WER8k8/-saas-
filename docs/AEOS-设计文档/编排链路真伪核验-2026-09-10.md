实测全库 grep：**没有任何地方调用** `HarnessGateway` / `ingest_user_intent` / `process_inbound_webhook`。它是**死代码**。

### ② 任务图：存在，但来自**硬编码模板**

`schemas/hermes_orchestration.py` 定义了 `TaskGraph` / `TaskNode` / `IntentEvent`（结构是好的）。

## 2. 唯一的真断点

**「需求 → 任务图」这一步没有 AI 实现。**

- 外层 `harness_gateway` 是死桩；
- 内层 `parse_graph_to_tasks` 无人调用；
- 今天能跑的图，全是代码里写死的场景模板。

所以你设想的效果——「**同一个入口，拆出不同的任务，调动不同的插件，得到不同结果**」——**目前只能靠改代码加模板实现，不能靠 AI 自动拆**。

## 3. 现在唯一能用的入口

```http
POST /api/v1/orchestration/tasks
```

`routes/orchestration.py:68 create_orchestration_task` → 建 `AiTask` → Celery `process_ai_task` → `dispatch_ai_task` → 按 `task_type` 路由 → 执行器。

这是**当前唯一可手工驱动整条链的入口**（`AiTask` 的三个创建点之一，另两个在 `task_control_supervisor` 和 `task_control.py`）。

## 4. 接通你的架构：最小改动路径

要让「Harness 智能拆解」真的工作，改动是**收敛的**，不用重构：

### 步骤 1 · 让拆解有产物（核心）
把 `deepseek_harness` 客户端（**已存在**：`services/deepseek_harness/client.py`，懒加载 SDK、`run_turn`）接上，让它产出 `TaskGraph`：

```
自然语言需求 → deepseek_harness.run_turn(prompt=拆解指令) → TaskGraph JSON
            → task_control_supervisor.parse_graph_to_tasks()  # 已有，接上调用即可
```

### 步骤 2 · 让入口真的调它
把 `harness_gateway.ingest_user_intent` 从桩改成真调用（或新开一个 `routes/orchestration.py` 的 `POST /tasks/from-intent`）。**注意**：`harness_gateway` 现在无人调用，改它之前先决定是复用还是废弃。

### 步骤 3 · 插件化收尾
- `accio` 补真实现（现在只有骨架）；
- `trade_ai` / `goodjob` 换真桥（`docs/TradeAI-GoodJob-Hermes总线对接方案` 已有方案）；
- n8n 工作流定义从 `active:false` 桩换真节点。

### 步骤 4 · 验收
一条自然语言需求进去 → 输出一份不同的 `TaskGraph` → 落到 `ai_tasks` 表 → 不同 `task_type` 走到不同执行器 → 结果回写 + n8n 出站。
