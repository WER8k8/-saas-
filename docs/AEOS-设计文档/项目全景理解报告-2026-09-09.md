## 0. 一句话结论

优丁 YouDing 是一套**面向建材外贸卖家的多租户 B2B 外贸 SaaS**：租户拥有独立域名官网，用 AI 写内容 → SEO/GEO 优化 → 分发到国内外约 40 个平台 → 流量回官网 → 询盘捕获到物流可查的七步闭环。工程上它是一个**两代架构并存、正处于收敛期的大型单体 + 多子系统项目**：后端内核（多租户、Hermes 编排、DeerFlow、Browser Runtime、建站与工程计算）是真实可跑的工业级代码，但**八大子系统中有三个（Trade AI Agent、GoodJob CRM、22 参数 BOQ 核价）在主后端仍是 mock 桩或根本不存在**，且官网前端存在「开发版 / 运行版」双形态分叉。文档体系本身也存在多处互相打架的口径，需以实测为准。

## 1. 产品与商业模式

**产品定位**：不是单点建站工具，而是「AI 卖货 OS」——把建站、内容生产、搜索优化、跨平台分发、询盘归集打包成一条链路，让不懂 SEO 的外贸卖家也能由 AI 副驾代管增长。

**五类角色与四壳**（与硬锁 ROLE-SHELL-LOCK-01 对应）：

| 角色 | 入口壳 | 职责 |
|---|---|---|
| 平台超管 | `/admin` | 平台运营、租户管理、计费、SEO 矩阵、AEOS 控制台 |
| 区域代理（L2） | `/partner` | 开户审批、区域分成 |
| 市级代理（L3） | `/agent/*` | 开户申请、业绩 |
| 租户 | `/client/*` | 自用后台 + UBrain 助手 |
| 海外买家 | 匿名官网 | 浏览、询盘 |

**计费三轨**（工作区口径）：SaaS 订阅（基础/专业/旗舰）+ AI Token（Token Wallet Guard 实时拦截）+ 静态 IP/指纹发布槽位。另有裂变奖励「呼朋唤友」。
> ⚠️ **口径冲突**：`docs/AEOS_MASTER_ARCHITECTURE_SPEC.md` 主张「七轨商业计费」，与工作区三轨说法不一致，属待决设计项（§10-11）。

**七步履约闭环**（GoodJob CRM 的核心叙事）：询盘捕获 → 需求核算 → 形式发票 PI → 定金核销 → 生产跟单 → 发运单证（CI / Packing List）→ 尾款与物流可查。

## 4. 后端架构

### 4.1 启动链与中间件（实测）

入口 `backend/app/main.py`（743 行）。`lifespan` 在 L503-544，**远不止初始化**——它按顺序拉起十余个 APScheduler 调度器（基础 rank/scenario-health/media-cleanup、Hermes 系的 nvidia probe / site patrol / greedy revenue / daily autonomous cycle、ops autopilot、deerflow、trade intel、nurture worker）。

中间件注册顺序（L558-608，Starlette 后注册者更靠外）：
`CORS` → `APISecurityHeaders` → `SecurityHeaders` → `Session` → `CSRF` → **`RequestSignature`（FIX-29 防重放）** → `WAF` → `Security` → `RateLimit` → `Performance` → `RequestId` → **`Tenant`** → `GZip` → **`BrandGuardResponse`** → **`NoFakeDeliveryResponse`** → `UnifyV1ApiResponse`。

后三个是项目特色守卫：品牌一致性、**假交付拦截**（与「交付求真」铁律呼应）、v1 响应统一封装。

路由机制：`pkgutil.iter_modules` 扫描 `api/v1/routes/`，凡模块导出 `router` 即自动挂载（`auto_discovery.py`）。这是路由数被文档低估的根源——散落在 `v1/` 顶层的 30 个模块也会被二次扫描挂载。

### 4.2 分层实况：名义分层，实际偏平

实测文件数：`api/` 240、`services/` 677、`models/` 94、`schemas/` 24、`core/` 67、`repositories/` **仅 5**、`db/` 5、`domains/` 14、`orchestration/` 4、`tasks/` 13。

`services/` 是巨型业务层，内含 43 个子域。但 `repositories/` 形同虚设，绝大多数 service 直接 `SessionLocal()`（`core/database.py:157` 自认 TODO[P2]），api 层也大量直接触碰 models。**「分层」在文档上是设计，在代码里是趋势**。

`domains/` 与文档不符：索引称「租户域名/多租户路由、tenant_middleware 主站白名单在此」，实测仅 `base.py`，真正的 `TenantMiddleware` 在 `core/`。

### 4.3 多租户隔离（核心，含一个真实缺陷）

隔离分两层：

**应用层**（主通道）：`services/tenant_scenario_service.py:135 resolve_tenant_id_for_user` 经 `user_tenants` 关联解析租户；`core/tenant_scope.py` 的 `scope_tenant_query` / `tenant_can_access` 给查询加 `tenant_id` 边界。由各租户域端点手动调用——**是约定，不是强制**。

**数据库层 RLS**（两套并存）：
- `db/rls_policies.py` 试点：6 张高风险表，由 `RLS_PILOT_ENABLED` 门控，**默认 False**（`config.py:65`）。
- `core/security/rls.py` 完整实现：自动扫所有含 `tenant_id` 的表建策略，用 `SET LOCAL app.current_tenant` 注入会话上下文（`_setup_rls_event_listener` 挂在 SQLAlchemy `begin` 事件上）。

**⚠️ 实测缺陷（建议优先修）**：`core/security/runtime_isolation.py` 自称「最后一道防线」，但其 `_get_current_tenant_from_context()`（L180-205）用 `contextvars.copy_context().get("_request")` 取租户——**传入的是字符串而非 ContextVar 对象，必然抛 TypeError 被 except 吞掉，恒返回 None**；且全库无任何中间件设置过名为 `_request` 的 ContextVar。结果是 `assert_tenant_access()` 永远走到「平台级请求不限制」分支直接 return True，**这道防御性校验实际是 no-op**。加上 RLS 试点默认关闭且 `force=False`（表属主旁路），生产环境的租户隔离**实际只靠应用层手写 filter 兜底**。

### 4.4 认证与授权

**双轨鉴权**（这是理解全项目接口调用的关键）：
- **BFF Cookie 轨**：`api/v1/admin_bff/` 的 `auth_adapter.py` 提供 `bff_login/bff_refresh/bff_logout`，Cookie 由 `core/jwt_cookie.py:set_auth_cookies` 下发（access HttpOnly/Lax、refresh HttpOnly/Strict）。前端 Vben 式管理端只消费 `/api/v1/admin-bff/*`，**不读 token**。
- **主 API Bearer 轨**：`core/security.py:109 get_current_user` 优先 `HTTPBearer`，无则回退 Cookie。

统一登录：`services/unified_admin_login.py:19 resolve_user_for_unified_login` 贯通主库 `users` 与 SEO 矩阵 `admin_users`，签发同一 JWT——这是 seo-admin 免二次登录的实现基础。

JWT 含 `jti` 黑名单 + Redis 会话吊销，bcrypt rounds 12/14。RBAC 为**静态矩阵 + DB 覆盖**双层：`core/permissions.py:51 ROLE_PERMISSIONS` 打底，`admin_auth.py` 查 `admin_roles/role_permissions` 表优先。
> ⚠️ 两套角色词表并存且不同构：DB 种子 4 角色（super_admin/seo_admin/editor/viewer），代码枚举 8 角色（含 admin/tenant_admin/sales/l2/l3）。**2026-09-10 直连实测：种子已灌（`admin_roles` 4 / `admin_permissions` 30 / `admin_menus` 31 / `role_permissions` 44），「种子为空」是过时说法。** 但词表分裂本身是隐患。

四壳落地路径：`core/jwt_cookie.py:196 resolve_home_path_for_role` — admin→`/admin`、tenant_admin/editor→`/client/today`、agent/sales/l2/l3→`/agent/performance`。

### 4.5 数据模型

94 个 model 文件按领域分组：租户域（tenant/region/platform_registry/vault/license/subscription）、用户域（user/admin/agent_tree/agent_commission_rule）、内容域（content/content_master/seo/eeat/ai_*）、获客域（inquiry/rfq/quote/opportunity/campaign/prospect_lead/email_outreach）、交易域（order/payment/invoice_application/shipping_timeline）、AEOS 域（ai_task/publish_task/token_ledger/deerflow_job/evolution/wangcai/ubrain_*）。

**外键弱**：大量 id 用 String(36)/UUID(as_uuid=False) 且无强 FK，参照完整性靠应用层。
**状态机**：`models/enums.py` 定义 `OrderStatus`（含 `_TRANSITIONS` 白名单）、`PaymentStatus`、`OpportunityStage`、`LeadStatus`；`ai_task.py:28 TASK_STATUSES`（9 态）是任务权威状态。
> ⚠️ **询盘状态无枚举**：`inquiry.py:24` 是裸 `Column(String(20), default="pending")`，流转散在 services 里——与「询盘状态机」的文档叙事不符。

### 4.6 迁移链（已钉死）

82 个迁移文件，**单 head = `105_reconcile_model_backfill`**，无断链。链非 001→105 线性，而是经 5 次 merge 收敛（`051`、`056`、`058`、`060`、`101`）。关键节点：`101_align_model_schema_conditional` 同时合并 `100_rls_batch1_trade_core` 与 `060_merge_all_heads`，统一迁移线；`105` 是链尾幂等兜底（`create_all` 补缺表）。

### 4.7 异步与任务队列

`tasks/celery_app.py` 注册 8 个任务模块、beat 调度若干；但 `task_routes` **只显式声明 3 个队列**（deerflow / default / cross_border），未声明 `task_queues`，其余靠任务名隐式路由。文档「7 队列」不实。
APScheduler 承担大量周期任务（随 app 启动）。
> ⚠️ **Temporal 不存在**：全库无 `import temporalio`。`orchestration/` 仅 `interfaces.py`（能力插槽契约）+ `executors/goodjob_executor.py`。文档「orchestration 含 Temporal 工作流」与代码不符。**DAG 实际由 `services/hermes/task_control_supervisor.py` 用 `AiTask` 表记录驱动**。

### 5.4 3000 运行源（Vite 版）

Vite 5 + Vue3 SPA，入口 `index.html → main.ts`。关键在**手写 Nuxt 兼容垫片** `composables/_nuxt-shims.ts`（563 行）：把 `useHead`/`$fetch`/`useAsyncData`/`navigateTo`/`useRuntimeConfig` 等挂到 `globalThis`，让 Nuxt 风格代码在 Vite 下跑通；配套 `_nuxt-app-module.ts`（别名 re-export）与 `_h3-shim.ts`（h3 空实现）。`vite.config.ts` 用别名 + `define: import.meta.client='true'` 收口。

## 9. 风险与技术债（分级）

### P0 — 影响商用或安全

1. **`runtime_isolation.py` 租户校验恒为 no-op**（§4.3）。叠加 RLS 试点默认关闭，多租户隔离实际只有应用层手写 filter 一层。建议：修复 ContextVar 取值、把 `RLS_PILOT_ENABLED` 纳入生产门禁、给 `scope_tenant_query` 加 pytest。
2. **Trade AI / GoodJob 是 mock 桩却产出「成功」信号**（§6-⑤⑥）。假邮箱、`status:"sent"`、硬编码银行账号与 PI 会污染 CRM 与单证。虽有 `NoFakeDeliveryResponseMiddleware` 兜底，但执行器层未覆盖。建议：给 mock executor 加显式 `simulated=True` 标记，或按对接方案接通真桥。
3. **`config/dev/.env` 的 Redis 配置违反 ENV-LOCK-01**（`REDIS_ENABLED=false` + `localhost`），是「全站转圈」的经典成因。
4. **`start.bat` 自检块失效**，一键启动可能静默失败（§7）。

### P1 — 工程健康度

5. **双后端 / 双管理端 / 双 inquiries**：SEO 逻辑同时存在于 `seo-backend/`（Node）与主后端 `api/v1/seo/` + `services/seo/`；admin 内自带 21+ 个 SEO 视图，与 seo-admin 12 页功能重叠；`api/v1/inquiries.py` 与 `api/v1/routes/inquiries.py` 并存。
6. **三套 API 客户端封装并存**（admin 的 fetch/axios/BFF-axios，官网的 useApi/$api/裸 fetch），`fetchWrapper.ts` 已标 `@deprecated` 但仍在。
7. **测试覆盖极低**：后端 54 个测试文件对数百个业务路由基本无覆盖；admin 318 view 仅 7 个测试文件，主要靠脚本门禁。
8. **备份文件残留**（`*.py.bak*` 十余处、`backend/_archive/`、`migrations/versions-backup-*`），违反「代码树内禁放备份」。
9. **角色词表分裂**：DB 种子 4 角色 vs 代码枚举 8 角色，不同构。
10. **RBAC / `/health` / CSRF 豁免等缺口**（TODO.md 技术债清单已列）。

### P2 — 收敛与整洁

11. **官网双形态已分叉**（§2.1），收敛路径 A/B/C 待决（`TODO.md` P0-14）。
12. **worktree git 链接损坏 + 运行源零提交**（§2.1），工程可追溯性缺失。
