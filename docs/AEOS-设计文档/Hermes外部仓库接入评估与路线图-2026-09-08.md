## 〇、30 秒结论

**第一个接入：deer-flow。** 理由一句话：它是唯一**业务价值最高**（深度研究+12 渠道发布，直达核心外贸链路）且**本地适配层已存在**（`app/services/deerflow/` 5 模块）的仓库——收编动作只剩"写一个 BaseExecutor 适配器"，而非从零移植。**但真正的第 0 步不是选仓库，而是接通断裂的派发链**：`ExecutorRegistry` 目前零消费者，`advance_plan()` 是 Stub——不接底座，收编任何仓库都无处派发。

## 二、四维评估矩阵

| 维度 | deer-flow | agency-agents-zh | ecc |
|---|---|---|---|
| **① 接入难度/耦合度** | 中。本地适配层已在（5 模块），只需写适配器桥接 `SubTaskExecutor`；难点=异步语义+state_machine 与 TaskGraph 的映射 | 低。`hermes/agency/` 已全套（loader/runner/bridge），包一层 BaseExecutor 即可；人格是 md 数据，零代码依赖 | 中偏高。68 agent 无任何引用，需新建人格 loader（可抄 agency 模式）；286 技能已通，但那是数据不是执行器 |
| **② 核心业务价值/风险** | **高价值**：深度研究（买家/市场调研）+ 内容发布 + 12 渠道，正在核心链上（leads→research→content→publish），今日 n8n 发布出站已实证。风险中：面最大、外部依赖多（搜索/LLM API、deer-flow-gateway 占 8000/8001 的历史包袱） | 中价值：276 人格/20 部门丰富计划层"谁来做"，提升产出质量，但不直接新增业务能力（76 业务技能已覆盖外贸主线）。风险低：纯数据人格 | **低价值（对租户业务）**：286 是工程技能（backend-patterns 类），服务开发而非外贸租户；且已有明确决策"默认关防稀释" |
| **③ 与 8 套编排组件冲突** | 中：deerflow 自带 planner/reviewer/state_machine，与 TaskGraph 语义重叠——解法：按"整体子计划委派"粒度收编（不拆 deerflow 内部状态机），n8n 出站保留在 deerflow 内部（今日链路不动） | 低：现有 `hermes/agency` 路径与任何编排组件无交叠 | 低：技能层已共存；但强行收编 agent 会与 agency 人格层职责重叠 |
| **④ 契约收编最小改造范围** | 1 个新文件 `executors/deerflow_executor.py`（≈150 行适配：`run()` → 构造 SubTask → 委托现有 `execute_subtask`）+ 注册 + 能力清单 | 1 个新文件 `executors/agency_executor.py`（≈100 行：`run()` → `workflow_runner.run_workflow_async`）+ 注册 | 若做：1 个 loader + 1 个 executor（≈200 行），但**建议不做**（见 §三） |

## 三、推荐结论与理由

### 推荐顺序：**deer-flow → agency-agents-zh → ecc（明确不做 agent 收编，维持技能数据层现状）**

**为什么 deer-flow 第一（而非难度最低的 agency）：**

1. **价值密度**：收编的目的不是"插件数量+1"，而是让 TaskGraph 长出真实的业务执行臂。deer-flow 承担的是创收链路（研究+发布+渠道），agency 只优化"计划质量"。先接通能产生业务动作的执行器，TaskGraph 才有验收意义。
2. **改造量其实不比 agency 大多少**：agency 虽简单，但 deer-flow 的本地适配层已经写好（executor/planner/reviewer/state_machine），收编 = 适配器而非移植。两者都是"一个文件 + 注册"。
3. **风险可控点已知**：今日刚实证 deer-flow→n8n 发布链路（6 条执行全 success），收编时**保持 deerflow 内部状态机为黑盒**、按"子计划委派"粒度对接，就不碰语义重叠区。
4. **agency 第二**的理由：它已经完成 80%（hermes/agency 全套可用），等契约底座搭好后包一层即得 276 人格，投入产出比极高，不该排在 ecc 后面。
5. **ecc 第三且降级**的理由：① 68 个 agent 收编会与 agency 人格层职责重复（人格层一个来源就够，否则路由要裁决"找谁"，徒增复杂度）；② 286 技能的价值已经通过 `skill_pack_loader` 兑现，再包一层无新增价值；③ "默认关防稀释"是已定口径。**ecc 的定位：技能数据源（保持现状），不是执行器插件。**

**其他选项说明**：
- `deepseek_harness`（今日刚接入的 routes+service）：适合作为第 4 个执行器（代码生成类任务），在 deer-flow/agency 稳定后视需求加。
- trade-ai-agent / goodjob-crm：是**应用级编排组件而非 agent 仓库**，不应收编为插件，应列入"降级/退役"清单（见 §四 Phase 3）。

## 四、接入路线图与每阶段验收标准

### Phase 0：契约底座接通（前置，任何收编前必做）★
- **改造**：`task_control_supervisor.advance_plan()` 去 Stub 化——按 `task_type=hermes_node:{executor}` 从 ExecutorRegistry 取执行器，异步执行 `run()`，写回 `ExecutorResult` 到 AiTask + trace/evidence；Celery 侧注册派发任务（复用今日已实跑的 celery 队列）。
- **验收标准**：
  1. 单元测试：注册一个 FakeExecutor，提交含 2 节点 TaskGraph，`advance_plan` 后两 AiTask 状态=succeeded 且 output 落库；
  2. accio 桩被真实调用一次（哪怕返回假内容），证明 registry 通路活；
  3. `orchestration_selfcheck.py` 仍 14/14；新增 1 项自检"executors registered ≥ 1 且 dispatch 通"。

### Phase 1：deer-flow 收编（第一个外部仓库）
- **改造**：新增 `executors/deerflow_executor.py`：`run(node, ctx)` 将 TaskNode 转为 SubTask → 委托 `deerflow/executor.py: SubTaskExecutor.execute_subtask()`；能力清单初版：`deep_research` / `seo_publish` / `multi_channel_publish` / `buyer_research`；deerflow 内部 `_notify_content_published`（n8n 出站）保持不动。
- **验收标准**：
  1. 回归：`tests/` 中 deerflow 相关验证套件 + 今日 n8n 出站链路（`trigger_sync` 200）全部不变红；
  2. 端到端：经 TaskGraph 提交一个 `seo_publish` 节点 → registry → deerflow → n8n 执行库出现新 success 记录（以今日 id=5 链路为基线）；
  3. 幂等：同一 plan_id 重放不产生重复发布；
  4. 证据链：执行写 trace（`trace_service`）+ evidence，失败路径写失败态不静默吞。

### Phase 2：agency-agents-zh 收编
- **改造**：新增 `executors/agency_executor.py`：`run()` → `hermes/agency/workflow_runner.run_workflow_async`；能力清单：`persona.*`（276 人格按部门寻址）；`AGENCY_ROLES_DIR` 指向 vendored 副本（不动 `_external` 原仓库）。
- **验收标准**：
  1. `list_roles()` ≥ 220 可寻址，抽 3 个部门角色经 TaskGraph 跑通；
  2. `greedy_agency_orchestrator` 既有行为零回归（它直接调 agency 路径，与契约插件并存不互斥）；
  3. LLM 路由失败时降级到规则模板，不阻断主链路（R-IDEA-10 零回归纪律）。

### Phase 3：ecc 维持现状 + 旧编排降级（收编收官）
- **不做**：ecc 68 agent 收编（职责与 agency 重复，价值不抵复杂度）。
- **做**：声明唯一总线（TaskGraph+supervisor+ExecutorRegistry+Celery），workflow_canvas/trade-ai-agent/goodjob-crm/Temporal/seo-backend+BullMQ 逐一评估降级为"只读参考"或归档。
- **验收标准**：
  1. 文档：`AGENTS.md` 增补"编排组件唯一来源"硬锁；`SKILL_PACK_SOURCES` 默认 business 的口径写入注释（已含）；
  2. 每退役一套编排组件：全库 grep 无活跃调用 + 自检 14/14 通过 + 归档（重命名不删除，守用户纪律）。
