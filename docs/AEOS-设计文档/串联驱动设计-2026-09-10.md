### 契约（已存在，设计优良）

`backend/app/schemas/hermes_orchestration.py` 已定义全套契约，**且字段是按"可编排"设计的**：

```python
IntentEvent    # 外层输出：intent + payload + context + reply_to
TaskGraph      # 任务图：plan_id + event_id + strategy + nodes + policies
TaskNode       # 节点：executor + capability + depends_on + input_from(JsonPath) 
               #      + sop_ref(ECC注入) + model_hint + retry + budget 
               #      + on_fail + compensation_action(Saga回滚)
GraphPolicies  # 图级：max_parallel + budget_cap + approval_required + degradation
ExecutorResult # 执行结果：node_id + status + output + evidence_id
```

**四个关键设计点（都已在契约里）：**
- `input_from` —— **JsonPath 数据总线**，跨节点取参（`'product_images': 'n1.output.urls'`）
- `sop_ref` —— **ECC 知识注入点**（节点级挂 SOP）
- `compensation_action` —— **Saga 逆向补偿**（如 `'site.draft.delete'`、`'budget.refund'`）
- `GraphPolicies.budget_cap` + `approval_required` —— **预算与人工审批闸**

## 2. 完整链路（现状时序，含断点）

```
外部触发（API / n8n webhook）
   │
   ▼
① IntentEvent ─────────────────────────── ✅ 契约在
   │
   │  ← 🔴【断点】缺「IntentEvent → TaskGraph」的拆解器
   │     harness_gateway 是桩（intent 硬编码 "inferred_from_harness"）
   ▼
② TaskGraph ───────────────────────────── 🟡 只有硬编码模板能产出
   │
   ▼ parse_graph_to_tasks() ────────────── ✅ 函数在，但无调用方
③ AiTask 父计划(hermes_plan) + N 个子任务(hermes_node:<executor>)
   │   无依赖 → created（可跑）；有依赖 → paused
   ▼ process_ai_task.delay（Celery）
④ dispatch_ai_task ────────────────────── ✅ 真
   │   ROUTERS[task_type] 或 hermes_node:<ex> → ExecutorRegistry.get(<ex>)
   ▼
   执行器执行 → ExecutorResult
   │
   ▼ advance_plan() ────────────────────── ✅ 真：依赖判定 + JsonPath 注入 + 派发下游
⑤ 结果回写 AiTask.output_json
   │
   ▼ 全部完成 → 父计划 done
   ▼ _notify_site_built → n8n 出站 ─────── ✅ 真
```

**断点只有一处：②的入口。** 其余全是通的。

## 3. 核心设计：拆解器（IntentEvent → TaskGraph）

### 3.1 接口

```python
# backend/app/services/hermes/planner_service.py（新建）
def decompose(intent_event: IntentEvent, db: Session) -> TaskGraph:
    """把意图拆成可执行的任务图。
    必须经过：模板匹配 → LLM 兜底 → 图校验 → 白名单过滤
    """
```

### 3.2 三种实现路径（推荐混合）

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A. 模板驱动 | 扩充 `templates/*_scenario.py`，按 intent 匹配 | 确定、快、免费 | 不灵活，加场景要写代码 |
| B. LLM 驱动 | 调 `deepseek_harness` 客户端产出 `TaskGraph` JSON | 灵活，能处理新意图 | 可能编造不存在的 executor |
| **C. 混合（推荐）** | **模板优先命中，未命中走 LLM，两者都过校验** | 兼顾确定性与灵活性 | 需维护两套 |

**推荐 C，因为**：项目已有模板机制（`site_build_scenario`/`outreach_scenario`），且 `deepseek_harness` 客户端已存在（`services/deepseek_harness/client.py`，有 `run_turn`）。两者都在，只需串起来。

### 3.3 三道安全阀（必须有，否则 LLM 拆解会失控）

```python
# 1. executor 白名单 —— 只允许注册表里真实存在的执行器
assert node.executor in ExecutorRegistry.list_executors()

# 2. 拓扑治理 —— 已有，直接复用
_validate_dag_topology(graph.nodes)   # 节点≤100 + DFS 环路检测

# 3. capability 白名单 —— 防止编造不存在的能力
assert node.capability in CAPABILITY_REGISTRY
```

> **不设这三道阀，LLM 会拆出 `executor: "super_agent_9000"` 这种不存在的节点，然后在执行层炸掉。** 项目此前 `fake_p0_executor` 的教训就在这里。

### 3.4 入口接通（二选一）

- **复用**：把 `harness_gateway.ingest_user_intent` 从桩改成真调用（注意它现在无人调用，改前先决定去留）
- **新开**：在 `routes/orchestration.py` 加 `POST /tasks/from-intent`，收 `IntentEvent` → `decompose()` → `parse_graph_to_tasks()` → 派发

**推荐新开接口**，保留旧桩不动（避免影响未知调用方）。

### 3.5 大模型驱动链路（补正 —— 原设计漏了这一层）

**拆解器用 LLM，但必须走对路。** 实测现状：

| 项 | 实测 |
|---|---|
| `get_ai_engine()` 是否单例 | ✅ 是 —— 43 个调用点共享同一实例 |
| tier 数 | 4（`general` / `high_quality` / `cost_optimized` / `deepseek`） |
| 能力标签 | 8（reasoning / coding / vision / writing / translation / structured_output / cheap / fast） |
| 走 `ModelGateway`（设计入口） | **仅 3 处** |
| 走 `ai_invocation_service` | 19 处 |
| **直连 `ai_engine`（绕过网关）** | **24 处** |

**结论：模型是「一个引擎、四个槽、多条路」——配置全局生效，但走哪个槽由场景决定；入口本该统一到网关，现在只有 3/43 走对了。**

#### 拆解器必须走 `ModelGateway`，不能直连 `ai_engine`

```python
# ❌ 错误：直连引擎，绕过网关
from app.services.ai_engine import get_ai_engine
result = await get_ai_engine().generate(prompt)

# ✅ 正确：走网关
from app.services.model_gateway import ModelGateway
result = await ModelGateway().generate(
    prompt,
    required_capabilities=["reasoning"],   # → logic tier，不是 general
    budget=...,                            # 受 GraphPolicies.budget_cap 约束
    privacy="strict",                      # 敏感租户数据 → 只允许境内 provider
    tenant_id=..., task_id=...,            # 成本记账归属
)
```

**三条理由：**
1. **成本记账** —— 拆解是高频调用，必须进 `model_call_ledger`，否则 Token 三轨计费断掉
2. **合规闸门** —— `privacy=strict` 只允许境内 provider（`DOMESTIC_TIERS = cost_optimized / deepseek`）
3. **预算控制** —— `GraphPolicies.budget_cap` 要靠网关的 ledger 才落得下去

#### 关于 DeepSeek

- **它注册进的是 `llms["deepseek"]` 和 `llms["cost_optimized"]`**（兼任成本优化档）
- 所以 **配了 DeepSeek ≠ 全部用 DeepSeek**：命中 `deepseek`/`cost_optimized` 才走它，`logic` 走逻辑模型，`multilingual` 走多语言模型
- **⚠️ 当前它根本没启用**：`_init_deepseek_llm()` 只在 `AI_DEEPSEEK_API_KEY` 存在时注册，而该 key 实测为空。当前实际走 bankofai 网关的 qwen3.8-flash + NVIDIA

> **要给拆解器上 DeepSeek，先做两件事**：① 配 `AI_DEEPSEEK_API_KEY`；② 确认拆解场景命中 `deepseek` 或让 router 的 `privacy=strict` 把它选中。

## 4. 12 个编排引擎的收敛设计

现状：**12 个引擎，只有 Hermes 是法定派发口，5 个绕过它自己开路由。** 收敛判据：

> **同时有「自己的路由 + 自己的状态机 + 自己的对外入口」= 平行系统（该降级）；只有前两者 = 执行器（该挂载）。**

| 类别 | 引擎 | 处置 |
|---|---|---|
| **法定中枢** | Hermes | 保留，作为唯一派发口 |
| **降级为执行器**（有独立路由，应收回） | UBrain / Paperclip / Wangcai / video_publish / workflow_canvas | 保留内部逻辑，**路由改为经 Hermes 派发** |
| **挂载进 ROUTERS**（无路由，直接注册） | DeerFlow（已挂）/ agent_loop / pipeline / orchestrator / growth_loop | 在 `ROUTERS` 注册 `task_type` 即可 |
| **作为横切机制**（不是引擎） | Evolution（自进化）/ Pipeline（关卡）/ Approval（审批门） | 做成 Hermes 流程里的**钩子**，不独立运行 |
| **契约层** | `app/orchestration/`（六插槽） | 补适配器，作为统一接入口 |

**收敛动作**：加场景 = 在 `hermes_task_bridge.ROUTERS` 注册一行（代码注释自己写的「加场景只改这里，不动 Hermes 主循环」）。

## 5. 分阶段落地

### P0 · 打通单链（不需要新代码，只需启动）

```bash
POST /api/v1/orchestration/tasks
{"task_type": "hermes_node:deerflow", "input_data": {...}, "auto_dispatch": true}
```
**目的**：先用现成入口跑通「派发 → 执行 → 回写 → n8n 出站」，证明调度层是好的。
**前置**：服务起来（`start-lan.bat`）+ 业务种子（`backend/seed.py`）。

### P1 · 接入拆解器（核心，~1-2 天）

1. 新建 `services/hermes/planner_service.py`：`decompose(IntentEvent) → TaskGraph`
2. 模板优先（复用 `templates/`）+ LLM 兜底（复用 `deepseek_harness.run_turn`）
3. 三道安全阀（executor / topology / capability 白名单）
4. 新开 `POST /api/v1/orchestration/tasks/from-intent`
5. 串上 `parse_graph_to_tasks()`

**验收**：一句自然语言 intent 进去 → 落出 `hermes_plan` 父任务 + N 个 `hermes_node:*` 子任务。

### P2 · 补执行器（让"不同插件出不同结果"成立）

- **Accio**：`models/ubrain_accio.py` + `accio_sales_service.py` 已有真逻辑，执行器只接了骨架 → 补真调用
- **Trade AI / GoodJob**：按 `docs/TradeAI-GoodJob-Hermes总线对接方案` 换真桥（`GOODJOB_BASE_URL` 未配置是当前断点）

### P3 · 收敛 12 个引擎

按 §4 的判据逐类处置。**这是让系统"一体化"的关键，优先级高于再引新项目。**

## 6. 验收标准（可测，不靠感觉）

| # | 标准 | 测法 |
|---|---|---|
| 1 | 单链跑通 | `POST /orchestration/tasks` → `ai_tasks` 出现记录且 status=done |
| 2 | 拆解可用 | 同一入口传不同 intent → 产出**不同的** `TaskGraph`（节点数与 executor 不同） |
| 3 | 插件可分派 | 不同 `task_type` 走到不同执行器（看 `hermes_node:*` 记录） |
| 4 | 数据总线通 | 下游节点能取到上游 `output`（`input_from` JsonPath 生效） |
| 5 | Saga 生效 | 故意让中间节点失败 → 触发 `compensate_plan` 回滚 |
| 6 | 出站通知 | 建站类任务完成后 n8n webhook 收到 POST |
| 7 | 无假成功 | mock 执行器的产出带 `simulated: true` 标记 |

**第 2 条是灵魂**——它直接对应你最初的诉求：「拆出不同的任务，调动不同的插件，得到不同结果」。

## 7. 风险与回滚

| 风险 | 应对 |
|---|---|
| LLM 拆出非法节点 | 三道安全阀（§3.3） |
| 拆解超预算 | `GraphPolicies.budget_cap` 已在契约里，接上即可 |
| 人工审批场景 | `approval_required` 字段已支持，接 Paperclip 审批门 |
| 收敛时打断现有链路 | 逐个引擎灰度：先双跑比对，再切流量（对齐 Qoder 方案的 B2 机制） |
| 回滚 | 拆解器是**新增模块**，不改 Hermes 主循环；出问题删掉新接口即恢复 |

---

## 8. 一句话总结

**你要的那个效果——「同一入口，拆出不同任务，调动不同插件，产出不同结果」——机制上只差一个 `decompose()` 函数。** 契约、调度、插座、回流全都是现成的，而且做得比大多数系统好。补上这一环，剩下的是**把 12 个引擎收敛成 1 个**，而不是再引第 13 个。
