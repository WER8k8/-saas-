## 摘要（Executive Summary）

**一句话定位**：超管后台不是"功能大杂烩"，而是面向 SaaS 运营方的**控制面（Control Plane）**——它只回答三个问题：**平台稳不稳、钱对不对、权限有没有失控**。租户的业务操作属于 `/client/*`，不属于这里。

**现状体检结论（三句话）**：

1. **资产极厚、治理断层**：前端 `views/admin/` 实测 **112 个页面**，后端 `/api/v1/super-admin/*` 实测 **26 个路由模块**，RBAC 五张表已建——**功能基本都在，缺的是秩序**。
2. **权限是"假的"**：菜单 SSOT 硬编码在前端 `platformShellMenu.ts`，后端 `admin_menus` 表 + `/super-admin/menus` 接口**建好但未接通**。前端隐藏菜单 ≠ 后端拦截请求，**越权访问当前仅靠前端自觉**。
3. **审计是散的**：日志分散在 5 张互不相通的表（`operation_logs` / `super_admin_login_logs` / `payment_ops_audit` / `site_audits` / `ubrain_action_audits`），**无统一时间轴**，出事后无法一条线还原操作链。

**本方案主线**：不新增功能域，而是完成 **"一收敛、二统一、三分级"**——
- **一收敛**：菜单与权限 SSOT 从前端**收敛到后端**（`admin_menus` + `admin_permissions` 单一真源），前端只做渲染。
- **二统一**：①统一审计（单一 `audit_logs` 主表 + 分域视图）；②统一鉴权入口（消除 `security.py` 与 `admin_auth.py` 两套并存的判定歧义）。
- **三分级**：配置分级（系统级 / 租户级 / 环境级）、数据权限分级（全平台 / 按租户 / 按代理域 / 只读）、菜单分级（运营 / 商业 / 治理 / 实验室）。

**交付节奏**：P0 地基（3 周）→ P1 治理（3 周）→ P2 商业（3 周）→ P3 智能（4 周）→ P4 体验（持续）。**P0 不做完，后面全是返工。**

## 1. 核心目标与用户角色

### 1.1 后台五大核心目标（按优先级）

| # | 目标 | 衡量指标 | 反面（失败定义） |
|---|------|---------|-----------------|
| G1 | **权限可控** | 每个端点可静态推导所需权限码；越权请求 100% 被后端拦截（403） | 前端隐藏菜单即认为安全 |
| G2 | **操作可溯** | 任意高危操作可在 1 次查询内还原"谁·何时·从哪·改了什么·改成什么" | 日志散落、只能查到"发生过" |
| G3 | **平台可观测** | 租户数/营收/Token 消耗/发布成功率/告警，一屏可见且数据口径唯一 | 同一指标三个页面三个数 |
| G4 | **配置可治理** | 所有运行时配置有归属、有版本、有变更审计、可回滚 | 改 .env 重启，出事查不到谁改的 |
| G5 | **运营可自助** | 租户开通/续费/配额调整/工单处理不需要研发介入 | 每个运营动作都要发工单找开发 |

### 1.2 用户角色矩阵

> 设计原则：**角色 = 权限集 + 数据范围 + 默认落地页**。三者必须同时定义，只定义权限不定义数据范围是常见的越权漏洞来源。

| 角色 code | 角色名 | 典型使用者 | 权限范围 | 数据范围（Data Scope） | 默认落地页 |
|-----------|--------|-----------|---------|----------------------|-----------|
| `super_admin` | 超级管理员 | 平台所有者 | `*:*` 全权限 | **全平台** | `/admin` 超管工作台 |
| `platform_ops` | 平台运营 | 运营团队 | 租户/内容/发布/告警 读写；**无财务写** | 全平台（财务只读） | `/admin/tenants` 租户总览 |
| `finance` | 财务 | 财务/出纳 | 计费/订单/发票/分润 读写；**无用户管理** | 全平台（无用户隐私字段） | `/admin/finance` 财务概览 |
| `support` | 客服 | 客服团队 | 租户只读 + 工单读写 + 会话查看 | **按分配租户** | `/admin/tenants` 租户总览 |
| `auditor` | 审计员 | 内审/合规 | **全模块只读** + 审计日志读写 | 全平台（只读） | `/admin/security/audit` 审计日志 |
| `tech_support` | 技术支持 | 研发运维 | 监控/日志/运行时/备份 读写；**无业务写** | 全平台（技术维度） | `/admin/system/command-center` |
| `readonly_observer` | 观察者 | 投资方/上级 | 仅看板只读 | **全平台聚合数据（无明细）** | `/dashboard` 数据看板 |

**关键规则（必须落到代码）**：
- `auditor` 角色的"只读"必须是**后端强制**（所有写端点拒绝），不能只靠前端隐藏按钮。
- `support` 的数据范围"按分配租户"需要**行级过滤**，对应 `admin_user_data_scope` 表（见 §5.1）。
- `readonly_observer` 只能看聚合看板，**不得返回租户 PII 明细**（手机号/邮箱需脱敏）。

### 1.3 角色与"四壳"的关系（不可越界）

依据 `ROLE-SHELL-LOCK-01`，超管后台属于 **Platform Shell**：

| 壳 | 前缀 | 登录角色 | 与超管后台关系 |
|----|------|---------|---------------|
| Client | `/client/*` | 租户老板/运营 | ❌ 租户看不到任何 `/admin/*` |
| **Platform** | **`/admin/*`** | **上面 7 个角色** | ✅ **本方案范围** |
| Agent | `/agent/*` | l2/l3 代理 | ❌ 代理登录后不得出现超管项（`四壳信息架构与菜单治理.md` §四明令禁止） |
| Login | `/login` | 全部 | 唯一登录入口（`LOGIN-LOCK-01`） |

## 3. 整体架构设计

### 3.1 五层架构

```
┌─────────────────────────────────────────────────────────────────┐
│ L1  壳层 Shell Layer                                             │
│     Platform Shell (/admin/*)  ·  路由守卫  ·  权限拦截器          │
│     产出：可访问性判定（能不能进）                                 │
├─────────────────────────────────────────────────────────────────┤
│ L2  导航层 Navigation Layer                                       │
│     动态菜单树（后端下发）· 三区 Tab · 面包屑 · 快捷搜索             │
│     产出：看得到什么（菜单可见性 = 权限投影）                       │
├─────────────────────────────────────────────────────────────────┤
│ L3  模块层 Module Layer（页面/视图）                               │
│     A~H 八大域 63 模块 · 统一页面骨架 · 统一空/载/错状态            │
│     产出：看得懂什么                                               │
├─────────────────────────────────────────────────────────────────┤
│ L4  领域服务层 Domain Service Layer（后端业务）                    │
│     鉴权 · 审计 · 配置 · 租户 · 计费 · AI治理 · 看板聚合            │
│     产出：能不能做（后端强制，前端不可绕过）                        │
├─────────────────────────────────────────────────────────────────┤
│ L5  数据层 Data Layer                                             │
│     PG@5433 · Redis@6379 · 234 表 · RLS · 预聚合指标表             │
│     产出：真相存哪                                                 │
└─────────────────────────────────────────────────────────────────┘
```

**关键约束**：**L2 的菜单可见性必须由 L4 的权限计算推导**，不得由前端常量决定。这是「一收敛」的架构含义。

### 3.2 请求链路（写操作示例：修改租户套餐）

```
用户点击「保存」
   ↓
[L1 壳层] 路由守卫：token 有效？角色属 Platform 壳？
   ↓
[L3 模块层] 前端发起 PATCH /api/v1/super-admin/tenants/{id}/plan
   ↓
[L4 服务层] ① 鉴权依赖 require_permission_code("tenant:plan:write") → 403 或放行
            ② 数据范围校验：该租户是否在 admin 的数据范围内？→ 403 或放行
            ③ 业务逻辑执行
            ④ **审计中间件**写入 audit_logs（含 before/after diff、trace_id）
   ↓
[L5 数据层] 事务提交 + 预聚合指标表异步更新
   ↓
返回统一信封 { code, message, data, trace_id }
```

**三个必须后端强制、前端不可信的检查点**：权限码、数据范围、审计留痕。

### 3.3 关键架构决策（ADR）

| # | 决策 | 备选方案 | 结论 | 理由 |
|---|------|---------|------|------|
| ADR-01 | 菜单 SSOT 归属 | ①前端硬编码（现状）②后端表+接口 ③混合 | **②后端 `admin_menus` 为唯一真源** | 现状①导致"前端删菜单≠后端拦截"，权限虚设。菜单即权限投影，必须同源 |
| ADR-02 | 路由注册方式 | ①静态 1930 行 ②按壳拆分静态 ③后端下发动态 | **②先拆壳拆分，③后续渐进** | 一次性动态路由风险高（首屏白屏/路径失配）；先拆文件降低耦合，再渐进去静态化 |
| ADR-03 | 权限判定统一 | ①保留两套 ②统一到权限码 | **②统一到权限码（`require_permission_code`）** | 枚举式 `require_role` 无法表达细粒度，且两套并存导致权限矩阵不可静态推导 |
| ADR-04 | 审计日志模型 | ①继续 5 表分散 ②建统一表+废弃旧表 ③建统一表+保留旧表做分域视图 | **③** | 旧表有业务耦合（如 `payment_ops_audit` 有专门 UI），直接废弃风险高；统一写入 + 视图汇聚是低风险路径 |
| ADR-05 | 配置存储 | ①.env ②DB 单表全放 ③DB 分级 + 加密列 | **③** | 密钥类必须加密存储且审计；普通配置需版本化可回滚 |
| ADR-06 | 指标数据来源 | ①实时 JOIN ②预聚合表 ③物化视图 | **②预聚合日表（`metrics_daily`）** | 234 表实时 JOIN 会拖垮主库；看板允许 T+1 或分钟级延迟 |
| ADR-07 | `super_admin` 通配处理 | ①保留 `["*:*"]` 隐式绕过 ②显式短路标注 | **②显式短路** | 隐式绕过在审计上不可见；显式标注后权限矩阵可推导 |
| ADR-08 | 前端组件库 | ①Ant Design Vue（现状）②换 Vben | **①维持 Ant Design Vue** | 换库成本极高且违反 DESIGN-TOKEN-LOCK-01 收敛方向 |

## 4. 前后端模块职责划分

> 判定原则：**任何"能不能"（授权/数据范围/审计）必须在前端之外的后端强制；任何"好不好用"（交互/展示/引导）在前端。**

| 域 | 前端职责（Vue3 + Ant Design Vue） | 后端职责（FastAPI） | 契约边界 |
|----|----------------------------------|-------------------|---------|
| **A IAM** | 菜单树渲染、权限矩阵 UI、会话列表、角色表单 | 权限码计算（`get_user_permission_codes`）、菜单树构建（`build_menu_tree`）、数据范围过滤、会话吊销 | 前端只渲染后端下发的菜单与 `permissions` 数组，**不自行拼装** |
| **B 租户运营** | 租户列表/详情 360 页、套餐配置表单、配额滑块 | 租户 CRUD、状态机流转、配额校验、域名 DNS 校验 | 状态流转规则在后端；前端只做按钮显隐 |
| **C 计费财务** | 订单/发票/分润列表、对账导出、金额格式化 | 计费引擎、支付回调、分润计算、**金额计算绝不过前端** | 前端展示由后端给的 `amount_cents`（分为单位，避免浮点） |
| **D 内容分发** | 通道健康面板、凭据表单（密文回显掩码） | 凭据加密存储、通道探测、发布任务调度 | 凭据明文**永不返回前端**，只返回 `last4` 掩码 |
| **E AI 治理** | 模型清单、场景路由配置、用量图表 | Provider 连通性测试、路由降级链、用量聚合、**熔断判定** | 熔断阈值在后端；前端只展示状态 |
| **F 数据看板** | 图表渲染（内联 SVG 或图表库）、下钻交互、导出触发 | 指标计算（`metrics_daily`）、口径字典、聚合 API | **指标口径由后端唯一提供**，前端不得自算 |
| **G 系统配置** | 配置表单（按类型渲染）、版本对比、回滚按钮 | 配置读写、加密、版本快照、变更审计 | 加密配置返回 `is_set: true` 而非明文 |
| **H 安全审计** | 审计检索 UI、时间轴、diff 查看、导出 | 审计写入（中间件）、检索、脱敏、留存策略 | 审计日志**只追加不可改**；前端无删除入口 |

### 4.1 前端改造重点（三条）

1. **菜单改为接口驱动**：`platformShellMenu.ts` 从"SSOT"降级为"**兜底默认值**"，运行时优先用 `/super-admin/menus` 返回值；接口失败才回退常量（保证可用性）。落地：`constants/platformShellMenu.ts` 保留，新增 `usePlatformMenu()` composable 做「接口优先、常量兜底」。
2. **路由按壳拆分**：`router/index.ts`（1930 行）拆为 `router/admin.ts` / `router/client.ts` / `router/agent.ts` / `router/partner.ts`（文件头注释本身已建议此方向）。
3. **统一页面骨架**：新建 `views/admin/components/AdminPageShell.vue`，强制统一 `loading / empty / error / forbidden(403) / no-permission(无权限码)` 五态，消除各页面自造状态。

### 4.2 后端改造重点（三条）

1. **鉴权收敛**：新增 `core/admin_guard.py` 作为**唯一超管鉴权入口**，内部委托 `admin_auth.py`，逐步替换散落的 `require_role` 调用，并在 CI 中加规则**禁止新增 `require_role` 于 `super_admin/` 目录**。
2. **审计中间件**：新增 `middleware/audit_middleware.py`，对 `/api/v1/super-admin/*` 的**写方法**自动落 `audit_logs`（含 before/after），减少手工埋点遗漏。
3. **指标预聚合**：新增 Celery 定时任务 `tasks/metrics_rollup.py`，每日聚合写入 `metrics_daily`，看板接口只读该表。

## 5. 关键数据模型设计

> 全部为**设计稿（DDL 草案）**。实际落地须写 Alembic 迁移，下一个迁移编号从 **119** 起（当前 head = `118_add_company_rfm_tags`）。

### 5.1 IAM 增强（在现有 5 表基础上扩展）

#### 新增表 1：`admin_user_roles`（管理员多角色）
**动机**：现状 `User.role_id` 为**单角色**外键（`models/user.py:21`），无法表达"某人既是财务又是审计员"。

| 字段 | 类型 | 说明 |
|------|------|------|
| id | UUID | PK |
| user_id | UUID | FK → `users.id`，CASCADE |
| role_id | UUID | FK → `admin_roles.id`，CASCADE |
| granted_by | UUID | FK → `users.id`，谁授的权 |
| granted_at | timestamptz | 授权时间 |
| expires_at | timestamptz | 临期授权（可选，NULL=永久） |

约束：`UNIQUE(user_id, role_id)`。
**兼容策略**：`User.role_id` 保留并回填到 `admin_user_roles`，代码先读新表、回退旧字段，**不删旧字段**（遵循"不删除、可恢复"原则）。

#### 新增表 2：`admin_user_data_scopes`（数据权限范围）
**动机**：`support` 角色只能看分配给他的租户，现状无任何行级隔离能力。

| 字段 | 类型 | 说明 |
|------|------|------|
| id | UUID | PK |
| user_id | UUID | FK → `users.id` |
| scope_type | varchar(32) | `all` / `tenant` / `agent_region` / `tag` |
| scope_value | varchar(200) | 按 type 解释：tenant_id / 区域码 / 标签 |
| created_at | timestamptz | |

**解析顺序**：任一 `all` → 全平台；否则并集；**无记录 = 无数据**（默认拒绝，fail-safe）。

#### 新增表 3：`admin_sessions`（会话治理）
**动机**：现状靠 Redis 吊销，无列表 UI，管理员看不到"谁在哪登录着"。

| 字段 | 类型 | 说明 |
|------|------|------|
| id | UUID | PK |
| user_id | UUID | FK → `users.id` |
| token_jti | varchar(64) | JWT 唯一标识，唯一索引 |
| ip_address | varchar(45) | |
| user_agent | varchar(500) | |
| issued_at / last_seen_at / expires_at | timestamptz | |
| revoked_at | timestamptz | 非空=已下线 |

## 6. 接口设计思路

### 6.1 规范基线

| 项 | 规范 |
|----|------|
| 前缀 | `/api/v1/super-admin/*`（已有，不动） |
| 资源命名 | 名词复数：`/tenants`、`/audit-logs` |
| 动作 | 动词交 HTTP 方法：GET/POST/PATCH/DELETE；非 CRUD 动作用子资源 `/tenants/{id}/freeze` |
| 分页 | `?page=1&page_size=20`，响应含 `{items, total, page, page_size}` |
| 排序 | `?sort=-created_at`（`-` 前缀表示降序） |
| 筛选 | 显式字段名 `?status=active&plan_id=xxx`；时间范围 `?start=ISO&end=ISO` |
| 统一信封 | `{code: 0, message: "ok", data: {...}, trace_id: "..."}`；非 0 为业务错误 |
| 错误码 | HTTP 语义 + 业务码分离：401 未登录 / 403 无权限 / 404 不存在 / 422 参数错 / 429 限流 |
| 幂等 | 写操作支持 `Idempotency-Key` 头（退款/发放类必须） |
| 版本 | 破坏性变更走 `/api/v2`，不原地改 |

### 6.2 权限码命名规范

格式：`{域}:{模块}:{动作}`，全小写，冒号分隔。

| 示例 | 含义 |
|------|------|
| `iam:menu:write` | 菜单管理写 |
| `tenant:plan:write` | 租户套餐写 |
| `tenant:quota:write` | 配额写 |
| `billing:refund:approve` | 退款审批 |
| `config:system:write` | 系统配置写 |
| `audit:log:read` | 审计读 |
| `*:*` | 超管通配（**显式声明，非隐式绕过**） |

**规则**：读用 `:read`、写用 `:write`、审批用 `:approve`、导出用 `:export`。**导出权限独立于读权限**（导出=数据外带，风险更高）。

### 9.3 状态规范（五态强制，消除自造状态）

| 状态 | 视觉 | 文案要求 |
|------|------|---------|
| 加载中 | 骨架屏（非转圈，减少跳变） | — |
| 空数据 | 插画 + 说明 + 主操作按钮 | "还没有租户，去创建第一个" |
| 无结果 | 区别于空数据（有筛选条件时） | "没有符合条件的记录，试试放宽筛选" |
| 出错 | 错误码 + 重试按钮 | "加载失败（500），请重试或联系技术支持" |

> 第 5 态是超管后台**特有且必需**的——权限矩阵设计下，能看到菜单但某页无权限是常态，必须有明确出口。

### 9.4 交互与可访问性

- **键盘**：全站 Tab 可达；焦点环 `2px solid var(--color-primary)`；`⌘K / Ctrl+K` 唤起全局搜索命令面板；`Esc` 关闭弹层。
- **对比度**：正文文本对比度 ≥ 4.5:1（WCAG AA）；主色 `#4a9b8c` 上的文字用白色时**仅限 ≥16px 粗体**，小字用深色文字避免不达标。
- **高危操作**：`--color-danger` + **二次确认弹窗 + 理由必填** + 操作后 Toast 显示可撤销窗口（`recycle-bin`）。
- **无损操作原则**：所有删除默认软删除进回收站（对齐 `G9`）。
- **零外链**：不引 CDN/外部字体/外部图表库；图表用内联 SVG 或项目已有图表库。

## 结语

超管后台的问题**从来不是功能不够，而是秩序不够**。112 个页面、26 个后端模块已经证明了开发能力；现在缺的是让它**可授权、可审计、可观测、可治理**的那层骨头。

**先做 P0 那 9 个"链主"模块**——菜单 SSOT、权限矩阵、数据范围、统一审计、配置中心、指标口径、工作台首屏。这九件事做完，后面 54 个模块才有地方长。
