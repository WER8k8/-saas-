## 0. 先说结论

**「不缺」不可能靠人或 AI 记全——只能靠机器校验。**

所以我做了个**能力台账**，把「系统能做什么」和「每件事串没串进编排」变成可重跑、可 diff 的清单。跑出来的答案是：

| 指标 | 值 |
|---|---|
| 路由模块 | **150** |
| 端点总数 | **1,384** |
| 服务子域 | 42 |
| 已注册执行器 | **4** |
| ROUTERS 派发键 | **4** |
| **已串联模块** | **2** |
| **串联率** | **1.3%** |

**整台机器有 1,384 个端点，编排链只够得着其中极小一部分。** 这不是危言耸听，是实测。

## 1. 为什么「记」不行，「台账」行

你的焦虑是真实的，而且**方法上就错了**——不是"谁不够努力"，是：

> 1,157 个后端文件 × 150 个路由 × 677 个服务 × 12 个编排引擎 × 9 个融合项目
> 这个组合量级，**任何"枚举式"的方法都必然漏**。

台账法的关键差别：

| 方法 | 可靠性 |
|---|---|
| 人/AI 读代码列清单 | ❌ 每次结果不同，必漏 |
| **脚本从源码生成台账** | ✅ 幂等，随时重跑，可 diff |

**改完代码重跑一次，串联率涨没涨、缺口少没少，一目了然。** 不依赖任何人的记忆。

## 2. 三类状态，就是三份待办

台账把每个模块判成三类：

| 状态 | 含义 | 数量 | 处置 |
|---|---|---:|---|
| **✅ 已串联** | 有 executor 或 ROUTERS 条目（Hermes 调得到） | 2 | — |
| **🟡 可串联** | 有路由有服务（能对外用），但不在编排链上 | **146** | ★ **主要补齐清单** |
| **⛔ 孤岛** | 只有服务没路由（潜在死代码） | 2 | 排查 |

**那 146 个就是你要的「不缺」清单**——它是有限的、枚举完毕的、可逐条消化的。

## 3. 「不缺」的正确定义

**这不是「把 150 个全串上」**——很多是后台 CRUD（`tenants`、`settings` 之类），本来就不该进编排。

**「不缺」= 每一个能力都有明确归属，没有悬空的。**

所以我建议给每个模块打**处置标签**（台账里加一列）：

| 标签 | 含义 | 例 |
|---|---|---|
| `orchestrated` | 该进编排，已串 | deerflow |
| `to-orchestrate` | 该进编排，待串 | seo_matrix / content / media_factory |
| `hook` | 该做横切钩子，不做执行器 | paperclip（审批门）、evolution（自进化） |
| `backoffice` | 只做后台管理，**明确不进编排** | tenants、settings、users |
| `deprecated` | 该废弃 | 待排查的孤岛 |

**判据**：当一个模块被贴上标签，它就"有归属"了；**台账里没有未标标签的模块，就是「不缺」。**

---

## 4. 落地三阶段

| 阶段 | 动作 | 产出 |
|---|---|---|
| **一、定归属** | 给 150 个模块逐个打上述 5 类标签 | 一份完整归属表，**没有任何模块悬空** |
| **二、按类处置** | `to-orchestrate` 的包成 executor（每个 50-100 行）；`hook` 的接进 Hermes 钩子；`backoffice` 的标注豁免 | 串联率从 1.3% 升到目标值 |
| **三、验收机械** | 重跑台账 → 检查「未标标签」为 0 + `to-orchestrate` 已全部 ✅ | **可机械判定"不缺"** |

**关键在第三步**——它把"我感觉差不多齐了"变成"台账里悬空项为 0"。这才是你要的那个确定感。

## 5. 台账怎么用（日常）

```bash
# 改完代码，重跑一次
python3 tools/capability_ledger.py

# 看三个数
#   ✅ 已串联      ← 应该在涨
#   🟡 可串联      ← 这你的待办
#   ⛔ 孤岛        ← 该排查
```

**建议把它接进 CI 或每次结构变更后跑**，这样"漏没漏"永远有客观答案。
