◆核心结论先看这五条

  1. 一句话定性：交易前有骨架，交易后基本空白，数据加工端大面积空转。这个系统「看起来有」的能力，远多于「实际生效」的能力 —— 而在生产环境里，这种状态比「明确缺失」更危险，因为它会被误信为「已经在跑」。
  2. 三条关键链路是断的。① 定时链路：生产 Docker 指向 app.core.celery_app.celery_app，而该变量不存在，worker 与 beat 都会在导入期崩溃；本机甚至连 beat 启动脚本都没有 —— 13 个定时任务一个都没在跑。② 归因链路：后台能解析 UTM，但前台从不发送 utm_*，且官网/租户站询盘从不写 attribution_channel → 归因报表里全部落 direct。③ 动作链路：流失预警、续费提醒、唤醒序列只算不做，算法写完了，没有触发方。
  3. 最致命的不是缺失，是「隐性失效」。四处典型：去重引擎 DedupEngine() 漏传 db 导致恒返回「非重复」；/lead/funnel 用了枚举里不存在的状态值，7 个阶段里 4 个恒为 0；丢单报表只遍历内存不读 PG，多进程下数据不完整；icp_score/account_score 有列无写入方，恒为 0。
  4. 有一处必须立刻处理的安全缺陷：/lead/export/csv 无租户过滤，修好属性名后会导出全租户线索 —— 现在是「必然报错」意外挡住了「跨租户泄露」。
  5. 大量高价值资产被浪费，补齐成本是「接线」而非「开发」。ai_recommendation_service（完整 UserCF/ItemCF 推荐算法，全库 0 引用）、growth_services（DB 版六维健康分 + NPS，0 引用）、subscription_countdown（完整 T-14/T-3/T-0 催续逻辑，0 调用方）、cadence_engine、buyer_360_enrichment —— 这些是现成的积木。
