体检结论

资产极厚，治理断层

三句话概括现状：功能基本都在，缺的是秩序。

① 资产极厚、治理断层

前端 112 个页面、后端 26 个路由模块、RBAC 五张表已建 —— 功能基本都在，缺的是秩序。

② 权限是「假的」

菜单 SSOT 硬编码在前端常量，后端菜单/权限接口建好但未接通。前端隐藏 ≠ 后端拦截，越权仅靠前端自觉。

③ 审计是散的

日志散落 5 张互不相通的表，无统一 trace_id。出事后无法一条线还原操作链。

方案主线 —「一收敛、二统一、三分级」： 一收敛＝菜单与权限 SSOT 从前端收敛到后端 admin_menus； 二统一＝①统一审计（单一 audit_logs + 分域视图）②统一鉴权入口（消除 security.py 与 admin_auth.py 双轨歧义）； 三分级＝配置分级（系统/租户/环境）、数据权限分级（全平台/按租户/按域/只读）、菜单分级（运营/商业/治理/实验室）。

§1

核心目标与用户角色

设计原则：角色 = 权限集 + 数据范围 + 默认落地页。三者必须同时定义 —— 只定义权限不定义数据范围，是越权漏洞最常见的来源。

后台五大核心目标

  • G1 权限可控 — 每个端点可静态推导权限码；越权 100% 返回 403
  • G2 操作可溯 — 一次查询还原「谁·何时·从哪·改了什么」
  • G3 平台可观测 — 关键指标一屏可见，且口径唯一
  • G4 配置可治理 — 有归属、有版本、有审计、可回滚
  • G5 运营可自助 — 开通/续费/配额/工单 不需研发介入

§3

整体架构设计

五层架构。核心架构约束：L2 的菜单可见性必须由 L4 的权限计算推导，不得由前端常量决定 —— 这就是「一收敛」的架构含义。

图 1 · 超管后台五层架构。L2→L5 的「权限投影」是本次收敛的架构关键。

STEP 2

require_permission_code("tenant:plan:write") → 403 或放行

STEP 4

L4 ② 数据范围校验

该租户是否在管理员数据范围内？→ 403 或放行

STEP 5

L4 ③ 业务执行

执行业务逻辑

STEP 6

L4 ④ 审计落库

中间件写入 audit_logs（含 before/after diff + trace_id）

STEP 7

L5 提交与聚合

事务提交 + 预聚合指标异步更新

三个必须后端强制、前端不可信的检查点：权限码、数据范围、审计留痕。 前端的任何隐藏/禁用都只是体验优化，不构成安全边界。

§7

页面五态规范（强制统一，消除自造状态）

状态视觉文案要求
加载中骨架屏（非转圈，减少跳变）—
空数据插画 + 说明 + 主操作按钮「还没有租户，去创建第一个」
无结果区别于空数据（有筛选条件时）「没有符合条件的记录，试试放宽筛选」
出错错误码 + 重试按钮「加载失败（500），请重试或联系技术支持」
无权限 403锁图标 + 申请入口「你没有查看该模块的权限，如需开通请联系超级管理员」
第 5 态（403）是超管后台特有且必需的 —— 权限矩阵设计下，「能看到菜单但某页无权限」是常态，必须有明确出口，不能白屏或报错。

交互与可访问性

  • 键盘：全站 Tab 可达；焦点环 2px 主色；⌘K / Ctrl+K 全局搜索；Esc 关弹层
  • 对比度：正文 ≥ 4.5:1（WCAG AA）；主色上小字避免纯白
  • 高危操作：危险色 + 二次确认 + 理由必填 + 可撤销窗口
  • 无损操作：所有删除默认软删除进回收站

移动适配（<768px）

  • 侧栏收起为汉堡菜单；Tab 变底部 Tab Bar
  • 表格转卡片列表，或允许横向滚动
  • 按钮最小点击区 44×44px；输入框字号 ≥ 16px（防 iOS 缩放）
  • 适配 iPhone 底部安全区 env(safe-area-inset-bottom)

§10

验收门禁与约束

P0 门禁（六条全绿才放行 P1）

  • 后端每一条 /super-admin/* 写端点都有明确 permission_code（无遗漏）
  • 越权测试：用 auditor 角色 token 调写端点，100% 返回 403
  • 审计完整性：随机抽 10 次写操作，10/10 有审计记录且 diff 可读
  • 菜单驱动验证：改 admin_menus.visible=false → 刷新后该菜单消失（无需改前端代码）
  • 数据范围验证：support 角色看不到未分配租户
  • 指标口径验证：metrics_daily 数值与手工 SQL 核对一致

每次施工后的通用门禁

  • 后端 pytest 通过
  • 前端 vitest + typecheck + lint 通过
  • 越权回归：新写端点用无权限 token 测，应 403
  • 审计回归：每次写操作产生审计记录
  • Alembic 单 head 校验（新迁移从 119 起）
  • 新产出登记到会话产出串联索引

不可违反的硬锁

锁 ID内容
DESIGN-TOKEN-LOCK-01平台主色 = 薄荷绿 #4a9b8c；禁止改主色、禁止硬编码其它主色、禁止恢复暗色切换
ROLE-SHELL-LOCK-01/admin/* 归 Platform 壳；代理登录后不得出现超管项
LOGIN-LOCK-01唯一登录 /login，禁止新建第二套登录页
ENV-LOCK-01PG@5433 / Redis@6379；禁止用空 SQLite 掩盖迁移问题
SYSTEM-LOCK-02八大子系统不可裁减 —— 超管后台须能观测全部八个

结语

超管后台的问题从来不是功能不够，而是秩序不够。 112 个页面、26 个后端模块已经证明了开发能力；缺的是让它可授权、可审计、可观测、可治理的那层骨头。

先做 P0 那 9 个「链主」模块 —— 菜单 SSOT、权限矩阵、数据范围、统一审计、配置中心、指标口径、工作台首屏。 这九件事做完，后面 54 个模块才有地方长。
