# 优丁 YouDing · 系统组装总方案

> **生成日期**：2026-09-09
> **配套文档**：`docs/项目全景理解报告-2026-09-09.md`（零件清单与实测结论）
> **目标终点**：全都要 —— ① 端到端主链跑通 ② 商用可收费 ③ 八大子系统真接入
> **已定原则**：允许保留桩，但桩必须防伪；先出方案，确认后再动手
> **一句话**：零件不缺，缺的是**接口层、边界层、规程层**这三层。

---

## 0. 诊断：为什么「零件全有」却组装不起来

用造车打比方，当前项目的真实状况是：

| 车的部件 | 系统对应 | 零件现状 | 缺的是什么 |
|---|---|---|---|
| 发动机 | DeepSeek Harness + AI 模型 | 仓库与适配器都在 | **没插油管**（AI Key 空、gateway 是 simulate 桩） |
| 传动系统 | Hermes DAG 编排 | 真实现（拓扑校验/Saga 都在） | 后接的执行器有两个是空转的 |
| 车轮 | Site / DeerFlow / Publish / Browser | 多数真实现 | 有一个轮子（BOQ 核价）**根本没装** |
| 转向与制动 | 租户隔离 / RBAC / 门禁 | 代码都在 | **刹车线没接**（隔离校验是 no-op、RLS 默认关） |
| 油箱 | PG / Redis / n8n | 都装着 | **油路接错**（生效的 env 里 Redis 是关的） |
| 仪表盘 | 自检 / 门禁 / 可观测 | 脚本都在 | 读数不可信（项数三口径、自检块失效） |
| 底盘 | 单一真相源 | — | **底盘是两半拼的**（官网双形态已分叉、worktree git 断链） |

**结论**：这不是一个「从零造」的项目，而是一个**装配工序没做完、且装配图纸自相矛盾**的项目。所以组装的第一步不是写新功能，而是**把规矩和接点定死**。

## 1. 装配第一原则：先立四条规程（规程层）

这四条不立，后面每接一个零件都会重新打架。

### 规程一：配置单一真源（**先搞清谁生效，再改**）

三份 env 并存。实测（跑真实 pydantic-settings 2.15.0 加载 + 读 `_read_env_files` 源码）**优先级从高到低**是：

| 优先级 | 来源 | 说明 |
|---|---|---|
| 1（最高） | **操作系统环境变量** | 部分脚本会注入，见下方「真正的风险」 |
| 2 | `backend/.env` | **dotenv 中最后加载 → 覆盖前者**；该文件头部注释已写明此规则 |
| 3 | `backend/config/dev/.env` | 被上面覆盖 |
| —（永不生效） | `backend/config/.env.dev` | **不在候选列表**，孤儿文件（点号位置与候选路径不同） |

加载逻辑在 `backend/app/core/config.py:31-36`：候选 `[ENV_FILE, config/{ENV}/.env, .env]`；pydantic-settings 按列表顺序读取并**后者覆盖前者**（源码 `dotenv_vars.update()`，已实测：列表 `[关, 开]` → 结果为「开」）。注意 `config.py:27` 的注释写的是「config/{ENV}/.env 优先，回退 .env」，**与实际行为相反**——这是代码注释本身的错，不要信。

**当前 Redis 值其实是对的**：生效的 `backend/.env` 里是 `REDIS_ENABLED=true` + `REDIS_HOST=127.0.0.1`，符合 ENV-LOCK-01。

**真正的风险在启动脚本**：以下脚本会把 `REDIS_ENABLED` 强制设成 `false`——操作系统环境变量优先级最高，env 文件救不了：`scripts/start-backend-strict.ps1`、`dev-backend-bootstrap.ps1`、`qa-s0-full-gate.ps1`、`run-full-checklist.ps1`、`run-traffic-local.ps1` 等。**用这些脚本起后端就会「全站转圈」。** 主启动脚本 `scripts/start-dev-admin.ps1` 不注入该变量，走 env 文件，是正常的。

**动作**：① 归档 `backend/config/.env.dev` 孤儿文件，避免后人改错；② 修正 `config.py:27` 的错误注释；③ 明确「开发启动只用 `start-dev-admin.ps1`」，并在上述 qa/strict 脚本开头加显式警告「本脚本会关闭 Redis」。

### 规程二：防伪标记规范（桩必须自证是桩）

当前 mock 执行器最大的危害不是「假」，而是**假得没有标记**——Trade AI 返回假邮箱、GoodJob 返回硬编码 PI 却带 `status: succeeded`，下游 CRM 与单证分不清真假。

**动作**：
- 定义统一约定：任何 mock/降级结果必须携带 `simulated: true`（或等价标记），并在响应、日志、UI 三处可见。
- 复用已有的 `NoFakeDeliveryResponseMiddleware`（`backend/app/core/no_fake_delivery_middleware.py`）思路，把它从「响应层拦截」下沉到「执行器层自证」。
- 为每个 mock 执行器加单测：断言其输出**必须**带 `simulated: true`，否则测试失败。这样将来有人偷偷把桩当真接，门禁会拦住。

### 规程三：每个接点一个端到端验收脚本

现在的「绿灯」大量来自桩空跑。**接点验收必须是端到端、可重复、且能证明数据真的流过**。

**动作**：每接一个子系统，就在 `backend/tests/` 或 `scripts/` 下补一个验收脚本，格式统一为「前置检查 → 触发 → 断言真实副作用 → 输出 PASS/FAIL」。已有的 `tests/rls_pilot_verify.py`、`tests/goodjob_bridge_verify.py`、`tests/task_chain_verify.py` 是正确范式，照它们写。

### 规程四：单一真相源 + 变更留痕

- **代码**：worktree 是唯一开发入口；修复它的 git 断链（见阶段 0）。
- **官网**：开发看 worktree Nuxt，运行看 `主要备份/上线网站/frontend`，中间靠同步脚本而非手工拷贝。
- **文档**：口径冲突以 `docs/多模型设计统一裁定书` 的三级链裁决，裁定后**回头改掉错文档**（全景报告 §10 已列 19 条）。

## 2. 依赖拓扑与关键路径

装配顺序由依赖决定，不能按「哪个子系统听起来重要」来排。

```
                         ┌─────────────────────────┐
    阶段0 地基 ──────────►│ env/Redis/PG/n8n/git/门禁 │  ← 所有东西的前提
                         └───────────┬─────────────┘
                                     ▼
                         ┌─────────────────────────┐
    阶段1 底盘 ──────────►│ 登录·四壳·RBAC·租户隔离·RLS │  ← 数据不串的前提
                         │      + Hermes 编排内核     │
                         └───────────┬─────────────┘
                                     ▼
              ┌──────────────────────┼──────────────────────┐
              ▼                      ▼                      ▼
   ┌──────────────────┐   ┌──────────────────┐   ┌──────────────────┐
   │ 阶段2 动力        │   │ 阶段3 入站/出站   │   │ 阶段5 资产        │
   │ Harness+DeerFlow │   │ Site/BOQ/发布/Browser│  │ skills/Agency/ECC │
   └────────┬─────────┘   └────────┬─────────┘   └────────┬─────────┘
            └──────────┬───────────┴──────────┬───────────┘
                       ▼                      ▼
              ┌──────────────────┐   ┌──────────────────┐
  阶段4 ─────►│ Trade AI + GoodJob│◄──┤ 需要上面全部供数 │
              └────────┬─────────┘   └──────────────────┘
                       ▼
              ┌──────────────────┐
  阶段6 ─────►│ 计费·支付·财务中台 │  ← 需要真实业务数据流
              └────────┬─────────┘
                       ▼
              ┌──────────────────┐
  阶段7 ─────►│ 收敛减重（双后端合一）│
              └──────────────────┘
```

**关键路径**：阶段 0 → 1 → 3 → 4 → 6。阶段 2 与 5 可以并行插入，但它们不阻塞主链。**阶段 7 必须最后做**，否则边收边分叉。

## 3. 分阶段装配计划

每阶段给出：目标 / 前置 / 要动的文件 / 验收标准 / 风险与回滚。工期按「单人熟练」估算，仅供排序参考。

### 阶段 0：装配台（环境地基）—— 让工位可用

**目标**：一套干净、可重复、自检可信的本地环境。

| 要动的点 | 具体动作 | 文件 |
|---|---|---|
| 配置真源 | 归档孤儿 `config/.env.dev`；修正 `config.py:27` 错误注释；明确开发只用 `start-dev-admin.ps1`（qa/strict 脚本会关 Redis） | `backend/config/.env.dev`、`backend/app/core/config.py:27`、`scripts/start-backend-strict.ps1` 等 |
| 启动脚本 | 修 `start.bat` 的杀端口行、迁移段、PowerShell 健康探测块（`^`/`$names` 被 cmd 抢先解释） | 工作区 `start.bat`、`_restart_verify.log` 对照 |
| 门禁口径 | 统一 `orchestration_selfcheck.py` 项数（14/18/19 三说），以实跑为准并把期望值写进脚本常量 | `backend/scripts/orchestration_selfcheck.py` |
| git 断链 | 重建 worktree 的 `.git` 指向真实仓，或明确改用真实仓操作 | `上线网站.worktrees/.../.git` |
| 备份清理 | 移除代码树内 `.bak*` 残留（十余处），移入 `_archive/` | 全景报告 §9-P1-8 已列清单 |
| 依赖固化 | 确认后端/前端依赖可重复安装（锁文件、Python 版本） | `requirements*.txt`、`package-lock.json` |

**验收标准**：
1. 一条命令起后端 + 官网 3000 + admin 5174，四端口均有进程且 `/health` 返回 200。
2. `orchestration_selfcheck.py` 实跑全绿，且项数固定可复现。
3. 后端日志出现 Redis 连接成功、无「降级为内存队列」告警。
4. worktree 内 `git status` 可正常执行。

**风险**：Redis 开启后若旧代码有阻塞式用法可能暴露新问题——回滚方式是把 env 两行改回并重启。

**工期**：1–2 天。

**目标**：数据不串、权限不越、任务能编排。**这是整个组装里最不能省的一步**。

## 6. 风险与回滚

| 风险 | 影响 | 对策 |
|---|---|---|
| 开 RLS 导致查询空集 | 功能大面积失效 | 先 6 张试点表，逐表验证再扩 |
| 开 Redis 暴露阻塞式用法 | 请求变慢/超时 | 保留 `REDIS_ENABLED=false` 快速回滚开关 |
| 真接入 Trade AI/GoodJob 后外部系统不稳 | 主链阻塞 | 每个执行器保留 `simulated` 降级路径 |
| 真实平台分发触发风控 | 账号被封 | 先用内部测试账号，限量分发 |
| 官网收敛改动大 | 官网不可用 | 收敛前给运行源建首个 git 提交，可回滚 |
| 配置改错文件（三份 env 陷阱） | 改了不生效 | 规程一：删孤儿文件，只留一份 |
