# 第一部分：项目一「别人开源项目」= GoodJob CRM

## 1.1 基础扫描

| 维度 | 实测结果 |
|---|---|
| 定位 | 外贸销售团队 CRM（客户/商机/跟进/获客/单证），"让业务员知道该跟谁、跟到哪步" |
| 技术栈 | Node.js + TypeScript（ESM）、npm workspaces monorepo；后端自建 Node HTTP 服务 + MySQL（`schema.mysql.sql` 3243 行 **131 张表**）；前端 React 19 + Vite + ECharts/globe.gl；队列 BullMQ；浏览器执行 Playwright MCP + CDP |
| 许可证 | **主体 Apache-2.0**（NOTICE 明示）；⚠️ `whatsapp-plugin/` 单独 **GPL-3.0-only**（依赖链含 libsignal） |
| 工作区 | backend（289 个 TS 源文件）、frontend、integration-sdk、integration-worker（MCP client/BullMQ/OAuth 连接器）、goodjob-runner（本机执行桥）、whatsapp-plugin（独立服务） |

## 1.2 核心模块与设计亮点（实测证据）

1. **Agent Skills 清单制**（`agent-skills/*/skill.json` + `agent-skills.ts`）：zod 严格校验的 manifest（id/version/category/status/triggers/keywords/modules/toolRefs/来源/许可证），**明确"Skill 只告诉 Agent 怎么做，Tool 执行可校验操作，Skill 不得扩权"**——与我方 §4.4 skills 表设计同构且更细。
2. **Agent Benchmark 闭环**（`agent-benchmark.ts` + `agent-mission-verifier.ts`）：每个用例有 goal/context/check，验证**结果而非回答**（"no fabricated email/phone"），输出 iterations/toolCalls/confirmationCount——正是我方缺失的"证据型评估"。
3. **模型治理**（`agent-model-governance.ts`）：按用途路由（planning/evaluation）、候选序列（≤3）、**按日/按任务双预算**、token 成本估算入账——与我方 §4.3 Model Gateway 设计完全同构。
4. **集成凭证库**（`integration-credential-vault.ts`）：AES-256-GCM + **AAD 绑定租户/属主/连接/工件类型**（防跨租户解密），密文格式 `v1.iv.tag.payload`——比我方 087 迁移草案更完整，AAD 思路直接吸收。
5. **获客执行引擎**（40+ 张 `prospect_*` 表）：campaigns/strategies 带版本与事件、执行 checkpoint/lease/重试、节流、Provider 请求台账+**记账证据**（`accounting_evidence`）、组织身份消歧（15 张 `organization_identity_*` 表）——是"证据引擎+幂等执行"的成熟参考实现。
6. **IAM/审批图**（`iam/`）：能力模型、自定义角色、MFA、审批图（approval-graph）+ outbox——对应我方 Policy Engine 升级方向。
7. **goodjob-runner**：本机拉取任务、受控浏览器（独立 Profile、仅 127.0.0.1、不读个人 Chrome 数据）——与我方 §4.9 Browser Runtime 合规红线逐条吻合。

| CRM 客户/商机/跟进 | 部分重叠 | 优丁有 companies/opportunities/crm_pipeline；GoodJob 更完整（考试/单证/提成） |

## 1.4 嫁接融合可行性报告（项目一）

### a) 可直接复用（设计/数据资产级）
- `agent-skills/*/skill.json` 的 **manifest 字段规范**（zod schema）→ 直接作为我方 `skills` 表（迁移 083）的字段蓝本，尤其 `triggers/toolRefs/sourceType/license`。
- **凭证库 AAD 设计**（tenant+owner+connection+artifact 四元绑定）→ 并入迁移 087，用现有 `gm_crypto`/`field_crypto` 的 SM4 实现同样语义。
- **Benchmark 用例格式**（goal/context/check + 反编造断言）→ 落为我方 Evolution 评估器的"证据型用例"模板。
- `agent-knowledge/` 10 份 JSON **业务契约文档**（客户/线索/获客/开发信/沟通/背调/操作契约）→ 作为 ECC 专家知识层种子语料（改造术语后入库）。

### b) 需改造后接入
- **模型治理模式**（用途路由+候选序列+双预算）：TS→Python 移植，落到 `model_gateway/router.py`；保留我方能力标签制（对方是用途枚举，二者合并为"能力标签+用途"双维路由）。
- **prospect 执行引擎模式**（checkpoint/lease/throttle/请求台账+证据）：不搬表，将其机制并入 `ai_tasks`（082 迁移追加 `lease_owner/lease_expires/throttle_key` 列）与 `task_traces`（085 追加 provider 请求台账字段）。
- **贸易数据 Provider 套件**（UN Comtrade 等 7 个）：以 Python 重写为 `trade_intel` 的新 Provider 类，包在现有 Provider 接口后（对方 TS 实现仅作参考）。
- **审批图（approval-graph）**：升级为全局 Policy Engine 的审批策略模块，替换/增强 `paperclip/approval_gate`。

### c) 不建议引入
- ❌ **`whatsapp-plugin` 代码级合并**：GPL-3.0-only 与商业闭源分发冲突（除非整体隔离为独立服务且接受 GPL 义务）；且 Baileys 走 WhatsApp Web 非官方协议，**封号+ToS 风险**，违反我方"官方 API 优先"红线。如确需免费通道：只能作为**独立进程侧车**通过 HTTP 对接，永不并入后端代码树。
- ❌ **MySQL Schema/后端整体**：131 张 MySQL 表 + Node 后端，与优丁 PG/Python 栈冲突，整体并入会破坏 Control Plane 唯一真相源。
- ❌ **React 19 前端**：违反 Nuxt 3 冻结；仅参考其信息架构（工作台/漏斗/地图分布页）。
- ❌ **goodjob-runner 的 Codex CLI 依赖**：本机执行桥思想吸收，但不绑定 ChatGPT/Codex 生态。

### d) 推荐集成方式
| 资产 | 方式 |
|---|---|
| Skill manifest 规范 / 凭证库设计 / 基准格式 / 知识语料 | **设计吸收**（写入迁移 083/085/087 与 ECC） |
| 模型治理、审批图、执行引擎机制 | **模式移植**（Python 重写到 Control Plane） |
| 贸易数据 Provider | **Adapter 接入**（重写为 trade_intel Provider） |
| WhatsApp 免费通道（若需要） | **独立侧车微服务**（进程隔离，GPL 边界清晰），官方 Meta 通道走现有 `whatsapp_business_service` |

### e) 与冻结架构兼容性
**兼容（有条件）**：GoodJob 的 Control Plane 思想（自有库为真相源、Skill 不扩权、工具可校验、凭证上下文绑定）与我方冻结口径高度一致；冲突仅在语言栈（TS vs Python，决定"模式移植"而非代码合并）与 whatsapp-plugin 许可证。**结论：作为"设计参考库 + 个别侧车"嫁接，不做代码合并。**

# 第二部分：项目二「别人开源2」= Trade AI Agent

## 2.1 基础扫描

| 维度 | 实测结果 |
|---|---|
| 定位 | 跨境电商智能营销自动化平台：社媒获客→清洗→AI 触达→智能回复→跟进→告警全链路 |
| 技术栈 | **Python 3.11 + FastAPI + SQLAlchemy 2 + Alembic + Celery + Redis 5 + PostgreSQL**；AI：LangChain + LangGraph + Chroma(RAG) + DashScope/OpenAI；前端 React 18 + AntD 5 + Zustand（21 页）；部署 Docker Compose + Nginx + GitHub Actions |
| 许可证 | README 声明 **MIT**（根目录无 LICENSE 文件——正式引入前需补书面许可确认） |
| 规模 | 后端 12 张表、80+ 路由、178+ pytest；E2E 212 Playwright；19 个 PR 有 Code Review 记录 |
| 来源 | Gitee（LBones-li/agent_trade_b），文档 21 份（架构/接口/测试验收/部署手册齐全） |

## 2.2 核心模块与设计亮点（实测证据）

> **2026-08-31 呼应更新**：本节已由源码级深度扫描补全，详见《项目二TradeAI可取之处评估报告_V1.0.md》。关键修正：① 完成度从"小而完整"上调为"**完整交付级**"（全库 0 TODO/FIXME/NotImplementedError，88 个 API 端点，28 个测试文件）；② 确认隔离模型为**仅 user_id、全库 0 个 tenant_id**，租户改造是唯一硬条件；③ 真正高价值资产收敛为：工作流引擎语义（暂停/恢复/打断/条件分支，`workflow_engine.py` 648 行）+ BaseSkill 运行时契约 + 三个算法件（表格多源归一/邮箱 MX 校验/时区调度）；④ 新增排除项：`skill_auto_sender` 的"随机间隔防封"策略（灰色反检测）与 `skill_social_scraper` 的 Apify/BrightData 抓取实现不予引入。

1. **`core/skill_base.py`（10.8KB）BaseSkill 插件基类**：`name/version/category/config_schema/input_schema/output_schema` + 状态机（PENDING/RUNNING/SUCCESS/FAILED/SKIPPED）+ SkillRegistry——**与优丁同语言同框架**，是现成的 Python Skill 契约。
2. **`core/workflow_engine.py`（24.6KB）工作流引擎**：`ExecutionStatus`（含 PAUSED/CANCELLED）、`StepCondition`（always/on_success/on_failure/custom）、`StepDefinition`（retry_on_failure/max_retries）——对应我方 deerflow 状态机缺失的"暂停/恢复"语义。
3. **8 个具体 Skill**：社媒抓取/数据清洗/Excel 读取/消息生成/自动发送/监控告警/**RAG 技能**——RAG 技能含 Chroma 向量检索接入，优丁 `vector_search_service` 可对照。
4. **`integrations/`**：邮件（SMTP/Gmail/Outlook OAuth）、WhatsApp Business（官方 API）、Google Sheets——均为 Adapter 式独立文件。
5. **工程纪律**：178+ 单测全过、`encrypt_account_credentials` 迁移（凭证加密已做）、RBAC 回填迁移、事件总线解耦（`core/event_bus.py`）。

## 2.3 与优丁的重叠/互补判断

| 域 | 关系 | 说明 |
|---|---|---|
| Skill 契约/注册 | **重叠但互补** | 优丁 `foreign_trade/skill_registry` 是文件级松注册；对方 BaseSkill 是更规范的类契约，正好补我方迁移 083 的 Python 侧落地 |
| 工作流引擎 | 部分重叠 | 优丁有 deerflow（缺 PAUSED）、agent_loop；对方引擎小而完整，状态语义可并入 |
| 社媒抓取/邮件/WhatsApp | 重叠 | 优丁已有对应服务；对方的 Gmail OAuth、Google Sheets 集成更整洁 |
| RAG 知识库 | 互补 | 优丁有 `knowledge_service`/`vector_search`；对方 Chroma 技能实现可作对照 |
| 可视化工作流前端 | **互补（优丁缺）** | 对方拖拽式节点编辑器（21 页之一）是优丁 admin 没有的能力形态 |
| 计费/租户/进化 | 优丁独有 | 对方无多租户计费、无 Experience Engine——我方是上位系统 |

## 2.4 嫁接融合可行性报告（项目二）

### a) 可直接复用（代码级，同栈）
- **`BaseSkill` + `SkillRegistry` 契约**：作为优丁 `skills` 表的**运行时执行层**（表管版本/权限，类管执行），二者天然配对；仅需注入 `TenantContext` 参数。
- **`StepCondition`/`StepDefinition` 条件步骤模型**：并入 `ai_tasks` 子任务执行器（补上"按上一步成败分支"能力）。
- **`ExecutionStatus.PAUSED/CANCELLED` 语义与暂停/恢复实现**：并入我方统一状态机（现行 9 状态增补 `PAUSED`，与 deerflow 的 checkpoint 恢复机制合并）。
- **事件总线 `event_bus.py`**：与我方 `core/event_bus.py` 对照（结构几乎相同，验证我方设计）；其"通知解耦"用法直接参考。

### b) 需改造后接入
- **8 个具体 Skill**：逐个包成优丁 `skills` 表记录（version/permissions/租户开关）后移植；`skill_social_scraper` 需先过合规审查（平台 ToS）；`skill_rag` 改接优丁现有向量服务与 `knowledge_ingestion`。
- **Gmail/Outlook OAuth 邮件集成**：并入优丁 `email_service`，凭证一律进 Credential Vault（对方 `encrypt_account_credentials` 迁移思路与我方 087 一致，可互相校验）。
- **可视化工作流编辑器（前端）**：以 Nuxt/Vue 重写（禁 React 并入），作为 admin 新页面；节点 DSL 与 `ai_tasks` 子任务 DAG 对齐。
- **`task_queue` 表模式**：不引入其表，映射到我方 `ai_tasks`。

### c) 不建议引入
- ❌ **其数据模型整体**（12 张表：customers/conversations/outreach_logs…）：优丁已有 224 表覆盖且更强，引入会制造双份真相源。
- ❌ **React 前端整体**：违反 Nuxt 冻结（仅吸收可视化工作流的交互设计）。
- ❌ **其单用户权限模型**：对方无真正多租户（`users` 单域），所有移植代码必须补 `tenant_id` 与 RLS 过滤，不得按原样接 API。
- ⚠️ **LICENSE 文件缺失**：README 声明 MIT 但无 LICENSE 文件；正式商用合入前必须取得书面确认或保留出处声明（Apache/MIT 均要求保留版权声明）。

### d) 推荐集成方式
| 资产 | 方式 |
|---|---|
| BaseSkill/Registry 契约、条件步骤、暂停/恢复 | **代码合并**（改造后并入 `app/core/` 与 `ai_tasks`） |
| 8 个 Skill | **Plugin 化**（注册进 `skills` 表，租户级开关） |
| 邮件/Sheets 集成 | **Adapter 接入**（并入现有 integrations） |
| 可视化工作流 | **前端独立开发**（Nuxt 重写，参考其交互） |

### e) 与冻结架构兼容性（深度扫描后维持原判）
**高度兼容**：对方就是"Control Plane（FastAPI 单体）+ Skill 插件 + 工作流引擎"的同构缩小版，无独立编排野心，天然可作为我方 Execution Plane 的 Skill/Workflow 供给源。唯一硬条件是**全部移植件补租户隔离**（深度扫描已证实对方全库 0 个 `tenant_id`）。结论：**两个开源项目中优先嫁接此项目**（同栈、MIT、质量门禁齐全、0 技术债标记）；逐文件级取舍清单见《项目二TradeAI可取之处评估报告》。

# 第三部分：总体裁决

| 排序 | 项目 | 裁决 | 首要理由 |
|---|---|---|---|
| 🥇 先接 | Trade AI Agent（开源2） | **代码级嫁接**（BaseSkill 契约 + 状态机增补 + Skill Plugin 化） | 同栈（FastAPI/SQLAlchemy/Celery）、MIT、可执行代码即我方迁移 083/082 的落地参考 |
| 🥈 后接 | GoodJob CRM（开源项目） | **设计级吸收**（Skill manifest/凭证库 AAD/基准/模型治理/审批图）+ 可选 WhatsApp 侧车 | 架构思想高度一致但语言栈不同，代码合并成本高于收益；GPL 插件严格隔离 |

## 红线复核（对照冻结架构）
1. ✅ Control Plane 唯一真相源：两项目数据模型均不并入，只并入契约/机制；
2. ✅ Harness 仅 Adapter：两项目均不引入新 Runtime 依赖，不触碰该边界；
3. ✅ 租户隔离优先：所有移植件强制 `tenant_id` + Repository 过滤 + RLS 试点表覆盖；
4. ✅ Skill 版本化：两项目的 Skill 规范统一收编进迁移 083 的 `skills/skill_versions` 表；
5. ⚠️ 许可证：GoodJob 主体 Apache-2.0（保留 NOTICE/归属）；whatsapp-plugin GPL-3.0 永不入代码树；Trade AI Agent 需补书面 MIT 确认。

## 建议执行顺序
1. 迁移 083（skills 注册表）按 GoodJob manifest 字段 + Trade AI BaseSkill 契约定稿；
2. 移植 Trade AI 的 StepCondition/PAUSED 语义进 `ai_tasks`（082 增补）；
3. 凭证库迁移 087 采纳 AAD 四元绑定设计；
4. Evolution 评估器采纳"证据型 benchmark"用例格式；
5. Trade AI 的 8 个 Skill 合规审查后逐个 Plugin 化；
6. GoodJob 贸易数据 Provider 按优丁接口 Python 重写；
7. （可选，最后）WhatsApp 免费通道以独立侧车评估，默认不做。
