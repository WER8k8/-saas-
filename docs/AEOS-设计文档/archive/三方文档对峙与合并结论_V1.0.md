# 三方文档对峙分析与合并结论 V1.0

> 对峙对象：
> - **A 方**：《GPT文档纠错与实现设计补充_V1.0.md》（本系统基于代码库实测产出的纠错与实现补充报告，下称"我方报告"）
> - **B 方**：Claude 三份总结（《AI_企业私有智能中心_完整实现规范_V2.md》2235 行、《测试体系与交付清单.md》864 行、《代码框架_完整版.md》1201 行）
> - **参照**：GPT 原始设计文档 6 份（双方共同纠错的对象）
>
> 总判定：**架构口径一致度约 85%，双方独立得出相同的核心结论（Control Plane 为中枢、Harness 仅 Adapter、经验飞轮不训模型）。但 B 方在"起点假设"上未对账代码库，仍是重建式设计；且 B 方代码样例含 5 处现网已修复过的回归型缺陷。可全部合并，前提是：以我方"存量增量演进"为主骨架，吸收 B 方的表字段设计、测试体系与评分权重，废弃 B 方的重建式脚手架代码。**

### 1.3 实质性差异（详见 §二 冲突判断）

1. **起点假设**：B 方三份文档整体仍按"新建 `ai-growth-os` 仓库、90 天从零 MVP"编写（新 Schema、新项目结构、新前端）；我方报告核心结论是"在现有 224 张表的存量系统上增量演进"（E8）。
2. **前端技术栈**：B 方全部 React + Redux（App.tsx/JSX 样例）；现网是 Nuxt 3 + Vue3（300+ 页 + 401 页 admin）。
3. **计费数据模型**：B 方新建 wallets/wallet_ledger/orders/invoices；现网已有 wallet/token_ledger/payment/finance_ledger（经 18 项 P0/P1 修复，含行锁/幂等/回滚自愈）。
4. **主键与 DDL 方言**：B 方 BIGSERIAL 整数主键 + MySQL 语法（`ENUM(...)`、表内 `INDEX`）混用 PG 语法（JSONB），在现网 PostgreSQL + SQLAlchemy 2.0 + UUID 主键体系下无法直接执行。
5. **DeerFlow 挂接位置**：B 方"DeerFlow 是 Harness 的 Plugin"；我方"Harness/DeerFlow 是平级 Adapter，都挂在 Control Plane 下"。
6. **ECC 定义**：B 方"ECC = 分散的 Skills/SOP/Validators，不是单一知识库"；我方 E1"ECC = 企业专家知识库"。语义可并（见 §四术语统一）。
7. **部署形态**：B 方 K8s Deployment 样例；我方 MVP 维持 docker-compose（E7）。
8. **状态机**：这是 GPT 三套之外的第四套（B 方版），但与我方基线是超集关系，非对立。

## 四、可合并性结论与合并原则

**可以全部合并且最终不冲突。** 合并原则如下：

1. **主骨架 = 我方报告**（存量 224 表 + 迁移 082-088 + P0-P5 路线 + E1-E16 纠错），因为它是唯一与真实代码库对过账的版本。
2. **从 B 方吸收（字段/资产级）**：
   - `evidence` 独立表（claim/verification_method/verified）→ 并入迁移 085
   - `artifacts` 表（版本/生命周期/创建者/存储路径）→ 并入迁移 085，补现网缺口
   - `validation_results` 五层验证结果 → 并入 085
   - `skill_performance` / `agent_scorecards` 记分卡 → 新增迁移 089
   - `pricing_rules`（flat/tiered/per_unit/percentage）→ 并入 086，挂现有计费
   - `attribution_models` 归因 → 新增迁移 089
   - Lead 意图评分权重（公司规模15%/行业15%/地区10%/紧迫度20%/预算15%/参与15%/历史转化10%）→ 校准现有 `lead_scoring_engine`
   - 测试体系全文（金字塔/质量门禁/安全用例/上线清单/24h 监控）→ 作为《测试规范》独立成文
3. **从我方必须保留**：技术栈冻结（Nuxt/compose/Redis+Celery）、计费不重建、状态机以 deerflow 为基线、RLS 三步走、Harness 仅桩、验收红线 5 条。
4. **统一术语表**（冻结，不得再用括号外名称）：

| 冻结术语 | 含义 | 废弃别名 |
|---|---|---|
| Control Plane | 现有 FastAPI 单体（唯一真相源） | "SaaS 控制平面""AI Revenue OS 后台" |
| Hermes | 内部编排模块（app/services/hermes） | "外层 AI Operating Layer""Nous Hermes" |
| DeepSeek Harness / DSH | 外部 Agent Runtime，仅 Adapter+桩 | "DeepSeek Hermes" |
| ECC | 专家能力层伞概念（Skills+SOP+验证器+专家面板+知识条目），**不是**执行沙箱 | "Execution Context Container" |
| Sandbox / Browser Runtime | 隔离执行环境 | "Accio 终端执行器" |
| Accio | 外贸获客业务服务（ubrain/accio_*） | "Work Runtime" |
| ai_tasks | 统一任务表 | tasks |
| task_traces | 统一 Trace 表 | agent_runs + task_execution_log（合并为一张） |
| meter_events | 计量事件表 | usage_events |
| experience_entries | 经验表（现有） | enterprise_experience |
| WAIT_HUMAN | 人审态（含审批） | WAITING_APPROVAL |

5. **抽象归位**：Harness/DeerFlow/n8n/Browser/Model = **Adapter**；ECC/Skills/SOP = **Knowledge/Service**；权限/预算/审批 = **Policy**（升级 paperclip approval_gate/budget_guard 为全局）；定价/套餐 = **配置表**（pricing_rules/plan_gate）。

## 五、最终建议（五档归类）

1. **完全一致**（直接生效，无需动作）：Control Plane 中枢、Harness 仅 Adapter、任务/凭证归自有库、n8n 外部化、Skill 版本化、多层验证、逐事件计费、经验可追溯、人审、租户隔离、术语纠错方向。
2. **表述不同但可合并**（按 §四术语表改名即可）：tasks↔ai_tasks、usage_events↔meter_events、agent_runs↔task_traces、enterprise_experience↔experience_entries、WAITING_APPROVAL↔WAIT_HUMAN、ECC 两种定义。
3. **有差异但可通过统一架构兼容**：状态机超集、DeerFlow 挂接位置、ECC 伞概念、K8s/compose 分期、测试门禁新旧分治。
4. **存在冲突但可通过调整边界解决**：B 方 schema 主键/方言（取 UUID/PG，B 方仅作字段参考）、计费模型（保留现有表，吸收 pricing_rules）、90 天清单（重排为存量改造任务）。
5. **不建议同时实现，需裁剪或延后**：
   - ❌ 裁剪：B 方新建仓库/新 Schema 执行脚本/React 前端/SQLAlchemy 1.x 样例/无行锁计费代码/全开 CORS；
   - ⏸ 延后：K8s 部署（V3+）、Browser Runtime（V2）、Harness 真实集成（等 DSH GA）、Managed Service 商业化模块（P4 之后）。

### 统一后的最终架构口径（一句话版）

> **以现有优丁后端（224 表模块化单体）为 Control Plane 唯一真相源；Hermes 为内部编排、DeerFlow/n8n/Browser/Harness 为平级可替换 Adapter；ECC 为专家能力层（Skills+SOP+验证器+专家面板）；统一任务面（ai_tasks+9 状态基线状态机）、统一计量（meter_events+pricing_rules）、统一 Trace/Evidence/Artifact（task_traces+evidence+artifacts）、统一经验飞轮（ExperienceEntry→评估→Canary→人审）；前端冻结 Nuxt 3，部署冻结 docker-compose；B 方 Claude 文档的表字段设计、测试体系、评分权重全部吸收，其重建式脚手架代码全部作废。**
