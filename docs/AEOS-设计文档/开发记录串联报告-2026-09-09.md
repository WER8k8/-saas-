## 7. 与组装计划的接口（顺序与前置）

从这些记录里能直接推出组装顺序的**硬前置**：

1. **先收口租户隔离，再谈组装**——Trae D1（裸查询 ~98%）+ RLS 默认关 + 本轮发现的 `runtime_isolation.py` no-op，三者叠加意味着**多租户隔离目前只有应用层一层**。任何跨子系统数据流（Trade AI 回写线索、GoodJob 回写单证）都会放大这个风险。
2. **先建 PG 验收环境，再谈验收**——测试只在 SQLite（D6），PG 专属特性（RLS/pgvector/JSONB/迁移方言）测不了。没有 PG 门禁的「全绿」不可信。
3. **先给「有桥无路」的组件补首个调用方**——Trae annex 的反零调用条款：`tradeai` 适配器与 `goodjob_executor` 均零调用方；而 `trade_document_bridge`（有 `cross_border /export-quote`）与 `customer_pool_projection`（有 `inquiries_unified`）已有调用方。**组装顺序应按「谁已有调用方」先走**。
4. **按批次依赖推进**（Qoder + Trae annex 一致）：批次 A（契约 + TradeAI 通车 + 票据）→ B（GoodJob 桥 + 获客环 + 单证桥）→ C（meter_events + task_traces + 预算闸）→ D（插件化验收 + 四处注册复核）。
5. **合规闸门先行**：TradeAI MIT 无 LICENSE 需书面确认（不阻塞内部）；GoodJob `whatsapp-plugin` GPL-3.0 永不入树；CI 需 grep 禁止违规 import。
6. **调度主权不破**：一切执行经 Hermes、一切结果回写真相层；GoodJob 内部队列降级为「只消费 UJ 下发任务包」，禁止分身直连。
