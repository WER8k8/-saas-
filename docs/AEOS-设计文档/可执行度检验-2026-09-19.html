六、风险清单（按优先级）

P0-1 · 对外官网（3000）实际不可访问
3000 端口被 worktree Nuxt3 薄荷旧版进程占用（命令行 --port 3002 却监听 3000），对全部 HTTP 请求返回 426 Upgrade Required。按「官网启动强制索引」，3000 应运行 主要备份/上线网站/frontend 的 Vite 暖白+砖橙版。当前状态 = 潜在买家打开官网即失败。
证据：Get-NetTCPConnection -LocalPort 3000 → PID 24736 = nuxi.mjs dev；curl 三次均 426，带 Upgrade 头返回 400。
修复：按强制索引启动脚本重启官网（Vite 版），停掉 worktree Nuxt 实例。
P1-1 · /api/v1/lead/funnel 返回 500（枚举契约破裂）
模型 EmailStatus 无 REPLIED 成员，但 lead_tools.py 用字面量 "replied" 做 status.in_(...)，列定义 validate_strings=True → 绑定参数即抛 LookupError。线索漏斗页=超管核心看板，必现崩溃。
证据：TestClient 复现 LookupError: 'replied' is not among the defined enum values. Enum name: email_status_enum。
修复：EmailStatus 补 REPLIED="replied" 成员（含迁移），或查询改用枚举成员。
P1-2 · /api/v1/workspace/prospecting/leads 返回 500（模型契约破裂）
workspace.py list_leads 访问 current_user.tenant_id，但鉴权返回的 User 模型无此属性（ORM 直查 PG 数据本身正常，2 行）→ AttributeError。社媒拓客线索列表=Trade AI 前端口碑页，必现崩溃。
证据：TestClient 复现 AttributeError: 'User' object has no attribute 'tenant_id'（workspace.py L65）。
修复：改用正确的租户归属字段（如 user.tenant_id 或经依赖注入取 tenant），并补契约单测。
P1-3 · 测试桩数据污染生产库（84 条）
ai_tasks 表中存在 84 条 hermes_node:fake_p0_executor 任务，该执行器只存在于 tests/ 测试夹具——说明某轮测试直接写入了真实 PG，而非隔离测试库。任务中心会展示伪任务，破坏数据可信度。
证据：PG 直查 SELECT count(*) FROM ai_tasks WHERE task_type LIKE '%fake%' = 84。
修复：测试库与生产库隔离（测试 DATABASE_URL 指向独立库），清理 84 条脏数据。
P2-1 · 自检脚本与运行态口径不一致（SQLite vs PG）
orchestration_selfcheck.py 默认环境连 SQLite（219 表），与运行态 PG（248 表）不同。门禁绿 ≠ PG 运行态无错（本轮 2 个 500 即 PG 侧）。
建议：自检脚本显式加载 backend/.env 的 PG 连接，并加「PG 模式下接口冒烟」门禁。
P2-2 · 已知降级/待真接入组件（负责人应知晓口径）
① Trade AI 真发：需 SMTP/WhatsApp Business 凭据，当前发送技能诚实降级（draft/degraded，不静默假成功）；② visual_studio：FF_INSTATIC_STUDIO=false 时返回 not_ready；③ AEOS 双 executor 仍为 mock 桩，待真接入。
这些是「诚实降级」而非故障，符合交付求真原则；但对外演示时需明确「演示数据非真实发送」。
