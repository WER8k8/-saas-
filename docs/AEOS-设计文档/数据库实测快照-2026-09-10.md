## 2. 更正（三处，包括我自己报告里的）

### 更正一：表数是 229，不是 225 也不是 239

- **实测 229**（`information_schema.tables where table_schema='public'`）
- ORM 模型声明 **225** 张（`__tablename__` 计数）
- 法典/注册表写的 **239** —— **数据库里找不到任何支撑**

所以 `AGENTS.md` 的「229 表」是**对的**；我此前的《全景理解报告》把「225」当成了表数，那是**ORM 声明数**，表述不准确，已在报告里更正。

**模型与库的漂移（重要）**：

- **库里存在、ORM 没有模型** 9 张：`alembic_version`（系统）、`keyword_ranking_history`、`model_call_ledger`、`model_capabilities`、`pipeline_runs`、`pipeline_steps`、`review_tasks`、`seo_competitors`、`step_evidence`
- **ORM 声明了、库里不存在** 5 张：`agent_commission_settlements`、`email_outreachs`、`token_ledger_entries`、`wallet_accounts`、`wallet_transactions`

> ⚠️ **这 5 张缺失表是真问题**：任何走到这些模型的代码路径，运行时都会抛 `relation does not exist`。更麻烦的是 `app/db/rls_policies.py` 的 RLS 试点映射正好指向 `wallet_accounts`、`wallet_transactions`、`token_ledger_entries` —— **三张都不存在**，所以 RLS 试点一旦开启就会直接报错。

### 更正二：RBAC 种子是满的，不是 0 行

WorkBuddy 09-06 记录「`admin_roles`/`permissions`/`menus` 0 行（seed 未灌）」，我沿用进了报告。**实测已灌**：4 / 30 / 31 / 44。这条已过期。

### 更正三：RLS 不是「全关」，是只开了 3 张

文档口径是「试点 6 张表、默认关」。实测是 **3 张已启用**（`content_masters`、`payment_orders`、`ubrain_tenant_memory`）。注意 `payment_orders` 不在原试点清单里，而清单里的 `prospect_leads`、`email_outreachs` 反而没开——**实际状态与设计不一致**。

## 3. 最关键的一条：库是空的

**229 张表里，只有 11 张有数据，218 张是空的。**

| 表 | 行数 |
|---|---|
| `skills` / `skill_versions` | 76 / 76 |
| `role_permissions` | 44 |
| `admin_menus` | 31 |
| `admin_permissions` | 30 |
| `ai_tasks` | 30 |
| `tenant_plans` | 6 |
| `admin_roles` | 4 |
| `egress_suppliers` | 3 |
| `tenants` | 1（`Test P0 Tenant`） |
| `alembic_version` | 1 |

**而业务表全是 0 行**：`users` **0**、`inquiries` 0、`orders` 0、`products` 0、`content_masters` 0、`prospect_leads` 0、`deerflow_jobs` 0、`task_traces` 0、`meter_events` 0。

### 这意味着什么

1. **没有用户，就没有登录。** 文档里的演示账号（`admin/admin123`、`tenant/tenant123`、`agent/agent123`）**在这个库里根本不存在**。所谓「端到端主链跑通」，现在连第一步都迈不出去。
2. **这个库是「迁移跑完了、种子只灌了平台层」的状态**——schema 完整（229 表 / 4817 列 / head 105），但没有一个租户业务实体。
3. **组装计划必须加一步：业务数据种子。** 原来我写的「阶段 1 让车能开」隐含假设了数据存在，实际不成立。

### 顺带挖到的证据

`ai_tasks` 的 30 条记录里，任务类型包含 `hermes_node:goodjob_crm`(6, done)、`hermes_node:trade_ai_agent`(6, done)、**`hermes_node:fake_p0_executor`**(4 done / 3 created / 3 paused)、`hermes_plan`(5 done / 2 planning / 1 executing)，最新一条时间 `2026-09-08 22:02`。

这直接印证了此前的判断：**那些「全绿」的编排验收，跑的是名为 `fake_p0_executor` 的桩执行器**，而 goodjob/trade_ai 的 6 次 done 也是 mock 产出。
